# FinGuardOps AI 리포트 상태 전이

## 1. 문서 목적

이 문서는 FinGuardOps의 AI 사건 리포트 생성 과정에서 사용하는 상태, 허용 전이, 실패·fallback·재시도와 정확 일치 캐시 원칙을 요구사항 수준에서 정의한다.

이 문서는 이후 비동기 AI 리포트 처리, ERD, Entity, REST API, 멱등성, 동시성 제어, 감사 로그와 AI 운영 지표 설계의 기준으로 사용한다.

구체적인 요청·실행·결과 관계와 API 응답은 `docs/02-architecture/domain-erd.md`와 `docs/03-api/ai-report-usage-api.md`를 따르며, 이 문서의 캐시·재시도 정책은 해당 최신 계약과 일치시킨다.

## 2. 문서 범위와 경계

이 문서는 HIGH·CRITICAL 사건을 중심으로 생성되는 AI 리포트의 요청, 생성, 정상 완료, 템플릿 fallback 완료와 최종 실패를 다룬다.

AI 리포트는 거래 위험 판단과 사건 조사를 돕는 참고 자료이다. 생성형 AI는 위험 점수·위험 등급, 거래 대응, 최종 판정과 사건 상태를 결정하지 않는다.

다음 항목은 확정하지 않는다.

- Java Enum, Entity와 DB 컬럼·제약조건·인덱스
- REST API 경로·DTO·상태 코드
- 구체적인 비동기 실행 기술과 큐 구조
- 재시도 간격과 구체적인 Timeout 값
- 모델 라우팅의 구체적인 점수와 조건
- 리포트 품질 검증 규칙
- Kafka 이벤트와 Consumer 구조

Kafka는 핵심 거래·탐지·사건 기능이 안정화된 이후 도입할 범위이다. 현재 AI 리포트 상태 전이가 Kafka를 필수 구성요소로 사용한다고 가정하지 않는다.

## 3. 용어 정의

### AI 리포트

사건의 Rule·ML 탐지 근거, 행동 타임라인과 담당자 확인 항목을 생성형 AI 또는 템플릿 fallback으로 정리한 참고 자료이다.

### 생성 요청

특정 사건과 탐지 결과·프롬프트·모델 버전 조합에 대해 리포트 생성을 요구한 외부 `AiReportRequest`이다. `aiRequestId`로 식별하며 Provider 호출이나 실제 실행 식별자로 사용하지 않는다.

### 생성 실행

실제 모델 호출 또는 템플릿 fallback 처리를 수행하는 `AiReportExecution`이다. `executionId`로 식별하며 신규 실행을 만든 요청과 진행 중 실행을 공유하는 요청은 같은 실행을 참조할 수 있다. 캐시 적중 요청에는 새 실행이 없다.

### fallback 리포트

LLM Timeout, Provider 오류 또는 출력 형식 검증 실패 후 Rule·ML 결과를 기반으로 템플릿 방식으로 생성된 리포트이다. 정상 LLM 리포트와 명확히 구분한다.

### 재생성

탐지 결과, 프롬프트 또는 모델 버전 변경이나 담당자의 승인된 요청으로 새 리포트 생성을 시도하는 것이다. 동일 요청의 재시도와 구분해야 한다.

### 정확 일치 캐시

동일 사건에서 탐지 결과, 프롬프트와 모델 버전까지 모두 같은 경우에만 기존 결과를 재사용하는 캐시이다.

```text
caseId
+ detectionResultVersion
+ promptVersion
+ modelVersion
```

Reason Code가 같다는 이유로 다른 사건의 리포트를 재사용하지 않는다.

## 4. 상태 목록

상태 후보는 다음 다섯 개를 유지한다.

- `PENDING`
- `GENERATING`
- `COMPLETED`
- `FALLBACK_COMPLETED`
- `FAILED`

현재 요구사항에서 불필요하거나 중복되는 상태는 없다.

- `PENDING`은 요청 접수와 실행 시작 전 대기를 구분한다.
- `GENERATING`은 모델 호출, 출력 검증, 승인된 재시도와 fallback 처리 중인 실행 단계를 나타낸다.
- `COMPLETED`와 `FALLBACK_COMPLETED`를 분리해 정상 LLM 결과와 템플릿 결과를 구분한다.
- `FAILED`는 LLM과 fallback 모두 사용 가능한 리포트를 만들지 못한 결과를 나타낸다.

취소, 재시도 대기, 캐시 적중과 재생성을 별도 상태로 추가하지 않는다. 재시도는 같은 실행의 시도 이력으로, 캐시 적중은 요청의 `cacheHit`과 결과 참조로, 진행 중 실행 공유는 `executionId`와 `executionShared`로 표현한다.

## 5. 상태별 의미

### `PENDING`

AI 리포트 생성 요청이 접수되어 연결된 실제 생성 실행이 아직 시작되지 않은 상태이다. 실행 대기 이유와 생성 시작 전 취소 가능 여부는 `TBD`이다. 완료 결과 캐시 적중 요청은 새 실행이 없으므로 `PENDING` 실행을 만들지 않는다.

### `GENERATING`

리포트 생성을 수행 중인 상태이다. 모델 선택, LLM 호출, 출력 검증, 승인된 자동 재시도 또는 템플릿 fallback 수행을 포함할 수 있다. 각 실제 Provider 호출은 같은 `executionId` 아래 별도 `ProviderCallAttempt`와 `attemptNumber`로 구분한다.

### `COMPLETED`

LLM 결과가 승인된 출력 형식과 품질 검증을 통과해 정상 AI 리포트가 준비된 상태이다.

### `FALLBACK_COMPLETED`

LLM이 사용 가능한 정상 리포트를 만들지 못했지만 Rule·ML 기반 템플릿 fallback 리포트가 준비된 상태이다. 화면과 운영 지표에서 `COMPLETED`와 구분한다.

### `FAILED`

LLM과 fallback 모두 사용 가능한 리포트를 만들지 못한 상태이다. `FAILED`는 AI 리포트 생성 실패만 의미하며 거래·탐지·사건 처리 전체 실패를 의미하지 않는다.

## 6. 텍스트 상태 전이도

정상 흐름은 다음과 같다.

```text
PENDING
→ GENERATING
→ COMPLETED
```

LLM 실패 후 fallback 성공 흐름은 다음과 같다.

```text
PENDING
→ GENERATING
→ FALLBACK_COMPLETED
```

LLM과 fallback 모두 실패한 흐름은 다음과 같다.

```text
PENDING
→ GENERATING
→ FAILED
```

승인된 자동 재시도는 상태를 추가하지 않고 `GENERATING` 중 같은 실행의 시도 이력으로 표현한다.

```text
GENERATING
├─ 최초 호출 Timeout 또는 연결 실패
├─ 같은 executionId에서 최대 한 번 자동 재시도
├─ 출력 형식 검증
└─ 최종 결과
   ├─ COMPLETED
   ├─ FALLBACK_COMPLETED
   └─ FAILED
```

완료된 정확 일치 결과를 재사용하는 캐시 경로는 새 실행의 상태 전이가 아니다.

```text
새 AiReportRequest와 aiRequestId 생성
→ 기존 AiReport 참조
→ cacheHit = true
→ executionId = null
→ executionShared = false
→ 원본 결과 상태인 COMPLETED 또는 FALLBACK_COMPLETED로 요청 종결
```

## 7. 허용 전이

### `PENDING` → `GENERATING`

- 전이 조건: 생성 실행 권한을 획득하고 동일 요청이 이미 실행·완료되지 않았음을 확인한다.
- 변경 주체: 시스템. Spring Boot가 업무 정합성과 요청 상태를 소유하고 FastAPI가 생성 작업을 수행할 수 있다.
- 생성되는 결과: 실행 시작 이력, 선택 모델·Provider와 관련 버전 후보
- 사건 상태 영향: 없음
- 거래 상태 영향: 없음
- 실패 시 처리: 실행 시작 여부가 불명확하면 중복 호출을 방지한 뒤 기존 결과를 확인한다.
- 재시도 가능 여부: 실행 시작 자체를 중복 재시도하지 않고 기존 활성 실행을 확인·공유한다.
- 감사 로그 여부: 필요

### `GENERATING` → `COMPLETED`

- 전이 조건: LLM 출력이 승인된 형식과 품질 검증을 통과한다.
- 변경 주체: 시스템. 생성 결과를 검증한 뒤 Spring Boot가 최종 업무 상태를 반영한다.
- 생성되는 결과: 정상 AI 리포트, 모델·프롬프트·탐지 결과 버전, 사용량·지연·비용 기록 후보
- 사건 상태 영향: 자동 변경하지 않음
- 거래 상태 영향: 없음
- 실패 시 처리: 저장 결과가 불명확하면 중복 리포트를 새로 확정하지 않고 기존 결과를 확인한다.
- 재시도 가능 여부: 동일 정확 일치 조건의 중복 요청은 기존 결과를 캐시로 재사용하며 강제 재생성하지 않는다.
- 감사 로그 여부: 필요

### `GENERATING` → `FALLBACK_COMPLETED`

- 전이 조건: LLM Timeout·Provider 오류·출력 검증 실패 등으로 정상 완료하지 못했지만 템플릿 fallback이 성공한다.
- 변경 주체: 시스템
- 생성되는 결과: Rule·ML 기반 fallback 리포트, fallback 사유와 원래 모델 시도 이력
- 사건 상태 영향: 자동 변경하지 않음
- 거래 상태 영향: 없음
- 실패 시 처리: fallback 저장 결과가 불명확하면 완료로 임의 표시하지 않는다.
- 재시도 가능 여부: 같은 정확 일치 조건의 강제 재생성은 허용하지 않는다. 탐지 결과·프롬프트·모델 버전이 변경된 새 조건은 별도 요청이다.
- 감사 로그 여부: 필요

### `GENERATING` → `FAILED`

- 전이 조건: LLM과 fallback 모두 실패해 사용할 수 있는 리포트가 없고 승인된 추가 시도를 종료한다.
- 변경 주체: 시스템
- 생성되는 결과: 최종 실패 사유, 시도한 모델·fallback, 재시도 가능 여부 후보
- 사건 상태 영향: 자동 변경하지 않음
- 거래 상태 영향: 없음
- 실패 시 처리: 사건 상세의 나머지 정보는 계속 조회·처리할 수 있어야 한다.
- 재시도 가능 여부: 같은 멱등성 키 재전송은 기존 실패 요청을 반환한다. 재사용 결과와 활성 실행이 없으면 새로운 멱등성 키의 요청이 새 실행을 만들 수 있다.
- 감사 로그 여부: 필요

## 8. 금지 전이

- 새 실행의 `PENDING`에서 생성과 검증 없이 바로 `COMPLETED` 또는 `FALLBACK_COMPLETED`로 전이하지 않는다. 캐시 적중 요청은 새 실행 전이를 만들지 않고 기존 결과 상태를 요청에 투영한다.
- `COMPLETED` 리포트의 중복 요청으로 동일 버전의 새 리포트를 무조건 생성하지 않는다.
- `FALLBACK_COMPLETED`를 정상 LLM 생성인 `COMPLETED`로 표시하지 않는다.
- `FAILED`를 거래 또는 사건 전체 실패로 해석하지 않는다.
- AI 리포트 상태 변경이 거래 상태, 위험 점수·등급, 위험 대응, 사건 상태나 최종 판정을 자동 변경하지 않는다.
- Reason Code가 같다는 이유로 다른 사건의 리포트를 재사용하지 않는다.
- 탐지 결과, 프롬프트 또는 모델 버전이 다른 결과를 정확 일치 캐시로 반환하지 않는다.
- 재생성 시 기존 완료 리포트를 이력 없이 덮어쓰거나 삭제하지 않는다.
- 중복 완료 응답이 먼저 확정된 결과를 임의로 교체하지 않는다.

완료·fallback 완료·실패 상태를 `PENDING`이나 `GENERATING`으로 직접 되돌리지 않는다. 새 처리가 필요하면 기존 이력을 보존한 새 `AiReportRequest`를 만들며, 완료된 동일 정확 일치 결과가 있으면 새 실행 없이 캐시로 재사용한다.

## 9. 전이 조건

- 모든 전이는 현재 상태, 대상 `caseId`와 탐지 결과·프롬프트·모델 버전을 확인해야 한다.
- 생성 시작 전에 같은 정확 일치 조건의 완료 결과를 먼저 확인하고, 없으면 진행 중 실행을 확인한 뒤 새 실행 생성 여부를 결정해야 한다.
- 정상 완료는 출력 형식과 승인된 품질 조건을 검증한 뒤에만 가능하다.
- fallback 완료에는 fallback 사용 여부와 원인을 명시해야 한다.
- 최종 실패에는 LLM과 fallback 각각의 실패를 구분할 수 있어야 한다.
- 재시도와 재생성은 목적과 버전 기준을 구분해야 한다.
- 거래·사건 상태와 AI 리포트 상태는 독립적인 정합성 경계를 유지해야 한다.

### 생성 시작 전 취소

취소 상태가 후보 목록에 없고 취소 권한·업무 필요성이 기존 요구사항에 정의되어 있지 않다. 취소 허용 여부, 취소 결과 표현과 감사 범위는 `TBD`이다.

### Timeout 후 재시도

Timeout 후 실제 Provider 처리가 완료되었을 가능성과 응답 유실을 고려해 같은 실행의 확정 결과를 먼저 확인해야 한다. 자동 재시도는 Timeout과 연결 실패에만 적용하며 최초 호출을 포함해 최대 2회, 즉 최대 1회만 재시도한다. 실제 재호출은 새 요청이나 새 실행이 아니라 같은 `executionId` 아래 다음 `attemptNumber`로 기록한다. 재시도 간격과 구체적인 Timeout 값은 `TBD`이다.

### Provider 오류 후 다른 모델 라우팅

모델 라우팅은 실행 시작 전에 승인된 사건 복잡도 정책으로 모델을 선택하는 처리이다. 비일시적 Provider 오류는 자동 재시도하지 않고 템플릿 fallback으로 전환한다. Provider 오류 후 다른 모델로 전환하는 별도 정책을 도입할지는 사용자 승인 사항이며, 도입하더라도 실제 모델 호출별 시도와 비용을 기록해야 한다.

### 출력 형식 오류

형식 오류 응답을 정상 완료로 표시하거나 자동 재시도하지 않는다. 템플릿 fallback으로 전환하고 모델·프롬프트 버전, 검증 실패 항목과 실제 발생 비용을 기록한다.

### 캐시 적중

새로운 `Idempotency-Key`의 요청에서 완료된 정확 일치 `AiReport`가 확인되면 새 `AiReportRequest`와 `aiRequestId`를 생성하고 기존 결과를 참조한다.

- `cacheHit = true`
- `executionId = null`
- `executionShared = false`
- `initiatingAiRequestId = null`
- `resolvedReportRef = 기존 AiReport`
- `sourceAiRequestId`는 결과→실행→최초 요청 계보에서 파생

이 경로에는 새 `AiReportExecution`, `ProviderCallAttempt`, 리포트 본문, 가상 토큰과 가상 비용을 생성하지 않는다. 같은 `Idempotency-Key`와 같은 요청의 재전송은 새 요청 이력도 만들지 않고 기존 `AiReportRequest`를 반환한다.

### 이미 완료된 리포트의 중복 요청

일반 재사용 의도의 동일 정확 일치 요청은 캐시 적중 정책에 따라 새 요청 이력과 기존 결과 참조를 남긴다. 동일 정확 일치 결과의 강제 재생성은 허용하지 않는다.

### 버전 변경 후 재생성

- 탐지 결과 버전 변경: 기존 리포트의 근거가 달라지므로 새 생성 후보
- 프롬프트 버전 변경: 출력 지침이 달라지므로 새 생성 후보
- 모델 버전 변경: 생성 모델 조건이 달라지므로 새 생성 후보

버전이 변경된 요청은 정확 일치 캐시 적중이 아니다. 자동 재생성 여부, 담당자 요청 필요 여부와 호출 제한은 `TBD`이다.

### 재생성 중 기존 리포트 보존

기존 완료 또는 fallback 리포트는 새 생성 결과가 확정되기 전까지 보존한다. 새 요청이 `PENDING`, `GENERATING` 또는 `FAILED`여도 기존 유효 리포트를 계속 제공하며, 현재 결과 선택 순서는 AI API 계약을 따른다.

## 10. 변경 주체

### 시스템

- 생성 요청을 접수하고 중복 여부를 확인한다.
- 상태 전이와 버전·사용량·비용·fallback 기록의 정합성을 관리한다.
- 승인된 모델 라우팅, 출력 검증과 fallback을 수행한다.
- 생성형 AI 결과로 거래 또는 사건 상태를 변경하지 않는다.

### FDS 분석 담당자

- AI 리포트를 참고 자료로 검토한다.
- 허용된 경우 리포트 재생성을 요청할 수 있다.
- 리포트 내용과 무관하게 조사 근거를 검토해 사건 최종 판정을 수행한다.
- 재생성 허용 횟수와 조건은 `TBD`이다.

### 플랫폼·클라우드 운영자

- 생성 지연, 오류, 모델 라우팅, 캐시, fallback, 토큰과 비용을 관찰한다.
- 승인된 운영 절차를 수행할 수 있지만 사건 최종 판정이나 AI 리포트 내용을 업무적으로 확정하지 않는다.

### 생성형 AI

- 사건 리포트 내용을 생성한다.
- 자신의 리포트 상태를 최종 확정하거나 거래 위험 판단·사건 상태·최종 판정을 변경하지 않는다.

## 11. 멱등성 고려사항

- 같은 생성 요청이 재전송되어도 동일 버전의 리포트와 사용량 기록이 중복 생성되지 않아야 한다.
- 동일 요청이 동시에 도착하면 하나의 실행만 생성 작업을 획득해야 한다.
- Timeout 후 재시도가 원래 요청과 별도의 정상 리포트를 중복 확정하지 않아야 한다.
- Provider의 지연 응답과 재시도 응답이 모두 도착해도 하나의 최종 결과만 유효해야 한다.
- 동일 fallback 요청이 여러 번 실행되어 같은 리포트와 비용·사용량 이력을 중복 생성하지 않아야 한다.
- 이미 완료된 정확 일치 요청은 기존 결과를 유지해야 한다.
- 서로 다른 키의 진행 중 정확 일치 요청은 새 요청 이력을 만들되 기존 `executionId`를 공유하고 `executionShared = true`로 기록해야 한다.
- 완료된 정확 일치 결과를 재사용하는 요청은 새 요청 이력을 만들되 실행과 Provider 시도를 만들지 않아야 한다.
- 탐지 결과·프롬프트·모델 버전 변경에 따른 정당한 재생성과 단순 중복 요청을 구분해야 한다.
- 멱등성 키 구조, 요청 식별자 생성 방식과 보존 기간은 후속 설계에서 확정한다.

## 12. 동시성 고려사항

- 같은 정확 일치 조건의 여러 요청이 동시에 `GENERATING` 실행을 획득하지 못하도록 해야 한다.
- LLM 정상 응답, Timeout 처리와 fallback 완료가 경합할 때 하나의 승인된 최종 상태만 확정되어야 한다.
- 늦게 도착한 LLM 응답이 이미 확정된 `FALLBACK_COMPLETED` 또는 `FAILED` 결과를 이력 없이 덮어쓰지 않아야 한다.
- 재생성 중에도 AI API의 현재 유효 리포트 선택 순서에 따라 기존 성공 결과를 제공한다.
- 버전이 변경되는 시점과 생성 시작이 경합하면 요청이 사용한 버전 조합을 고정해 기록해야 한다.
- 캐시 기록과 영속 결과가 불일치할 때 정합성의 기준이 되는 저장소와 복구 정책은 `TBD`이다.
- 낙관적 락과 비관적 락 중 하나를 확정하지 않는다.

## 13. 실패·재시도 원칙

- AI 리포트 실패는 거래 판단 실패가 아니다.
- AI 리포트 실패가 사건 상태를 자동 변경하지 않는다.
- fallback 리포트는 정상 LLM 리포트와 구분한다.
- `FAILED`는 거래·사건 처리 전체 실패를 의미하지 않는다.
- LLM Timeout, 연결 실패, 비일시적 Provider 오류와 출력 형식 오류를 서로 구분해 기록한다.
- 출력 형식 오류 결과를 정상 리포트로 제공하지 않는다.
- Timeout 또는 연결 실패는 같은 실행에서 최대 한 번 자동 재시도한다.
- 출력 형식 오류와 비일시적 Provider 오류는 자동 재시도하지 않고 템플릿 fallback으로 전환한다.
- fallback도 실패하면 `FAILED`로 전이한다.
- 재시도 간격과 구체적인 Timeout 값은 이번 문서에서 확정하지 않는다.
- 재시도와 재생성에 따른 실제 호출량, 토큰, 지연시간과 비용을 누락하지 않는다.
- Redis 장애 시 정확 일치 조건을 우회하거나 다른 사건의 리포트를 재사용하지 않는다.
- Kafka는 현재 필수 흐름이 아니다. 향후 도입 시 중복 메시지에도 리포트와 비용 데이터의 멱등성을 보장해야 한다.

## 14. 감사 로그 요구사항

다음 변경과 처리 결과를 감사 가능하게 기록해야 한다.

- 생성 요청 접수와 생성 시작
- 상태 변경
- 사용한 `caseId`, 탐지 결과 버전, 프롬프트 버전과 모델 버전
- 모델·Provider 선택과 라우팅 사유 후보
- Timeout, Provider 오류와 출력 형식 검증 실패
- 재시도와 다른 모델 전환
- fallback 사용 여부·원인과 결과
- 캐시 적중·미적중과 처리 결과
- 중복 요청과 멱등 처리 결과
- 담당자의 재생성 요청
- 실제 LLM 호출량, 입력·출력 토큰, 지연시간과 비용 연결 정보 후보

감사 기록에는 다음 정보가 필요하다.

- 변경 사용자 또는 시스템
- 변경 시각
- 변경 대상
- 이전 값
- 변경 후 값
- 변경 사유 또는 처리 사유
- 관련 `caseId`
- 관련 `transactionId` 후보
- `aiRequestId` 후보
- `executionId` 후보
- `traceId` 후보

민감한 프롬프트 원문, LLM 입력·출력과 인증정보를 AuditLog에 기록하지 않는다.
AuditLog의 V7 물리 기반은 구현되었지만 AI action, 실제 AI 업무 통합, AI 사용량
Entity와 보존 기간은 확정하지 않는다.

## 16. 후속 ERD·API 설계 항목

후속 설계에서는 다음 항목을 사용자 승인으로 구체화해야 한다.

- 사건과 하나 이상의 AI 리포트 생성 요청·버전의 관계
- 리포트 상태, 본문, fallback 여부와 실패 사유의 분리 표현
- 탐지 결과·프롬프트·모델 버전의 고정 및 이력 구조
- 정확 일치 캐시 키와 영속 결과 연결 방식
- `aiRequestId`, `executionId`, `executionShared`, `ProviderCallAttempt`를 구현 모델에 반영하는 방식
- 상태 전이와 리포트 저장의 트랜잭션·동시성 경계
- 중복 요청, 늦은 응답과 fallback 경합 처리 계약
- 기존 리포트 보존 및 최신·이전 버전 조회 계약
- 확정된 오류·재시도·무실행 캐시 응답을 구현 모델에 반영하는 방식
- AI 사용량·토큰·지연·비용 및 감사 로그 연결
- Kafka 도입 이전과 이후에도 유지할 멱등성 요구사항

이 문서는 구체적인 Java Enum, Entity, DB 컬럼·제약조건, API 경로, DTO, 상태 코드와 Kafka 이벤트를 확정하지 않는다.
