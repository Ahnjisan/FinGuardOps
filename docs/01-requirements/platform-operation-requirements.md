# FinGuardOps 플랫폼 운영 요구사항

## 1. 문서 목적

이 문서는 FinGuardOps의 플랫폼·클라우드 운영자가 서비스 상태, 성능, 장애, AI 사용량과 비용을 확인하고 대응하기 위한 운영 요구사항을 정의한다.

이 문서는 다음 후속 작업의 기준으로 사용한다.

- 플랫폼 운영 화면 와이어프레임
- Observability 메트릭 명세
- 운영 알림 정책
- 장애 실험과 복구 검증
- AI 비용 및 FinOps 실험
- 배포 및 운영 이력 설계

운영 요구사항은 기술 이름의 나열이 아니라 다음 흐름으로 정의한다.

```text
운영 대상
→ 확인할 정보
→ 이상 상태
→ 운영자 행동
→ 기록 항목
```

본 문서는 플랫폼·클라우드 운영자의 운영 요구사항을 정의한다. 금융거래 탐지 시나리오와 FDS 분석 업무는 `fds-user-scenarios.md`에서 정의한다. 아키텍처, 구체적인 메트릭 이름, 경보 임계값과 구현 방식은 후속 문서에서 확정한다.

## 2. 범위와 문서 경계

FinGuardOps는 금융거래와 사용자 행동을 기반으로 이상거래를 탐지하고, 위험 대응과 사건 처리를 지원하며, AI 서비스의 장애·성능·비용을 통합 관리하는 Cloud Native 금융 AI FraudOps 플랫폼이다. 기존 금융 FDS 기능을 유지하면서 금융 FDS, AI 운영, Cloud Native 운영의 책임을 구분한다.

| 관련 문서 또는 영역 | 이 문서와의 경계 |
| --- | --- |
| 금융 FDS 사용자 시나리오 | 금융거래·행동 이벤트의 분석 흐름, Rule·ML 근거 검토, 사건 상태 관리와 최종 판정은 `fds-user-scenarios.md`에서 정의한다. 이 문서에서는 해당 흐름의 가용성과 장애 영향만 다룬다. |
| 시스템 아키텍처 | 서비스 책임, 통신 구조, 동기·비동기 경계와 장애 격리 구현은 `docs/02-architecture/`의 후속 문서에서 확정한다. |
| Observability 메트릭 명세 | 구체적인 메트릭 이름, 레이블, 수집 주기, 집계 방식과 보존 기간은 후속 메트릭 명세에서 확정한다. |
| 장애 실험 | 장애 주입 방법, 성공 조건, 복구 목표와 실험 절차는 후속 장애 실험 문서에서 확정한다. |
| API 명세 | 운영 API를 포함한 엔드포인트, 요청·응답과 상태 코드는 `docs/03-api/`에서 사용자 승인 후 확정한다. |

처음부터 전체 시스템을 MSA로 분리하지 않는다. 핵심 거래·탐지·사건 기능을 먼저 안정화하고 Kafka와 Kubernetes는 그 이후 단계적으로 도입한다. 이 문서에 포함된 운영 대상과 요구사항은 목표 및 계획 범위를 포함하며, 문서 작성만으로 구현 완료된 것으로 간주하지 않는다.

요구사항, 임계값, 아키텍처, API·DB 설계, 장애·비용 실험과 최종 검증은 사용자가 결정하고 승인한다. 측정하지 않은 비용 절감률이나 성능 향상은 운영 성과로 기록하지 않는다.

## 3. 플랫폼·클라우드 운영자

플랫폼·클라우드 운영자는 다음 업무를 수행한다.

- Spring Boot Backend와 FastAPI AI Service의 상태를 확인한다.
- API 응답시간·오류율·처리량을 확인한다.
- PostgreSQL·Redis와 Kafka 도입 이후의 Kafka 상태를 확인한다.
- Rule 실행시간, ML 추론시간과 AI 리포트 생성시간을 확인한다.
- DB Connection Pool과 Kafka 도입 이후 Consumer Lag을 확인한다.
- 모델별 LLM 호출량, 입력·출력 토큰과 비용을 확인한다.
- 정확 일치 캐시와 템플릿 fallback 상태를 확인한다.
- 장애 발생 시 영향받은 서비스와 거래 접수·탐지·사건·AI 리포트 기능의 범위를 판단한다.
- 현재 배포 버전과 변경 이력을 확인하고 배포 전후 이상 징후를 비교한다.
- 승인된 절차에 따라 임시 대응을 수행하고 원인, 조치와 후속 과제를 기록한다.

플랫폼·클라우드 운영자는 FDS 사건의 `NORMAL`, `FALSE_POSITIVE`, `CONFIRMED_FRAUD` 최종 판정을 수행하지 않는다. 위험 점수·위험등급·거래 대응 정책과 사건 상태를 임의로 변경하지 않으며, 운영 장애 정보가 필요한 경우 FDS 분석 담당자와 사용자에게 영향 범위를 전달한다.

## 4. 운영 대상 시스템

| 운영 대상 | 역할 | 현재 도입 상태와 운영 범위 |
| --- | --- | --- |
| Spring Boot Backend | 거래 접수·검증, 멱등성, 거래·사건 상태, 위험 대응과 업무 정합성의 최종 소유자 | Health, 거래·멱등·행동 이벤트, DetectionResult·DetectionEvidence, FraudRule·RuleVersion과 기본 Rule 집합 발행 경계, Rule 분석 HTTP Client·내부 오케스트레이션, External Risk 독립 정책·Mock, FraudCase·CaseTransaction과 위험 대응·AuditLog 원자적 최종화 경계가 구현되었다. Backend Java v2 DTO·Mapper·Client, 실제 Provider·거래 접수 전체 연결, Snapshot v2·운영 복구, 공개 사건·감사·최종화 API, USER 인증·인가와 사건 조사 상태 전이·추가 연결·병합·분리는 미구현이다. |
| FastAPI AI Service | Feature 계산, Rule 실행, ML 추론, 모델 라우팅, AI 사건 리포트와 템플릿 fallback | `POST /api/v1/rule-analysis`, External Risk 필수 입력의 `POST /api/v2/rule-analysis`, R001~R004 실행과 점수·RiskLevel·Evidence 계산은 구현되었다. v2 External Risk는 validation-only이며 ML 추론·모델 라우팅·AI 사건 리포트와 템플릿 fallback은 미구현이다. |
| PostgreSQL | 거래, 행동 이벤트, 탐지 결과, 사건, 감사 로그와 AI 사용량·비용 데이터의 영속 저장 목표 | V1~V7의 거래·멱등·행동 이벤트, DetectionResult·DetectionEvidence, FraudRule·RuleVersion, FraudCase·CaseTransaction과 append-only AuditLog 영속 기반이 구현되었다. External Risk 영속화와 사건 조사·AI 사용량·비용·운영 데이터는 미구현이며 별도 승인 범위이다. |
| Redis | 정확 일치 AI 리포트 캐시와 집계 데이터 사용 목표 | 향후 연동·검증 범위이다. External Risk cache는 현재 계약이 아니며 별도 Issue와 승인이 필요하다. 시맨틱 캐시는 범위에 포함하지 않는다. |
| Kafka | 사건·리포트·통계 등 비동기 처리 목표 | 핵심 거래·탐지·사건 기능 안정화 이후 도입한다. 현재 구현된 구성으로 간주하지 않는다. |
| External Risk Mock | 위험 송신·수신 계좌와 위험 기기의 결정적 scenario 제공 | local/dev/test 전용 독립 Port·정책 Service·Mock과 성공 인메모리 Snapshot이 구현되었다. 실제 Provider·IP·거래 접수 연결은 미구현이며 실패를 cache·fallback·`UNMATCHED`로 변환하지 않는다. |
| LLM Provider | HIGH·CRITICAL 사건 중심의 생성형 AI 사건 리포트 생성 | 향후 외부 연동 범위이다. 위험 점수, 최종 판정, 거래 차단, 고객 제재와 사건 상태 확정을 수행하지 않는다. |
| Observability Stack | 로그·메트릭·트레이싱 수집 및 기술 상태 분석 | 핵심 기능 안정화 이후 단계적으로 도입할 범위이다. 논리 메트릭 계약은 `observability-metrics-spec.md`에 정의했으며 제품 선택과 실제 수집 구현은 후속 범위이다. |
| 배포 환경 | 로컬·컨테이너·클라우드 환경에서 버전 배포와 실행 상태 관리 | Docker, CI/CD, Kubernetes와 AWS는 로드맵에 따른 단계적 도입·검증 대상이다. Kubernetes와 AWS가 현재 구현된 것으로 간주하지 않는다. |

## 5. 공통 운영 식별자

다음 식별자는 장애 분석과 거래 접수부터 탐지·사건·AI 리포트까지의 처리 흐름 추적에 사용한다.

| 식별자 | 운영 목적 |
| --- | --- |
| `transactionId` | 특정 거래의 접수, 분석, 대응과 관련 오류를 연결한다. |
| `caseId` | 사건과 관련 거래, AI 리포트, fallback과 운영 영향을 연결한다. |
| `eventId` | Kafka 도입 이후 이벤트 발행·소비·중복 처리 흐름을 추적한다. |
| `aiRequestId` | 외부 AI 리포트 요청, 요청자, 멱등 처리와 요청 상태를 연결한다. |
| `executionId` | 실제 AI 논리 실행, 재시도, fallback과 연결된 Provider 호출들을 묶는다. |
| `attemptId` | 개별 실제 Provider 호출의 토큰, 비용, 지연과 결과를 식별한다. |
| `traceId` | Spring Boot, FastAPI, External Risk Mock, LLM Provider 등 서비스 간 호출 흐름을 연결한다. |

식별자는 로그·메트릭·트레이스와 운영 이력을 상호 연결할 수 있어야 한다. 구체적인 생성 방식, 데이터 타입, 전파 헤더, 저장 위치와 보존 기간은 이번 문서에서 확정하지 않으며 `TBD`로 둔다. 식별자에 API Key, 인증정보나 개인식별정보를 포함해서는 안 된다.

## 6. 서비스 상태 요구사항

정확한 경보 임계값, 확인 주기와 자동 복구 방식은 모두 `TBD`이며 후속 메트릭·알림·아키텍처 문서에서 확정한다.

| 운영 항목 | 운영자가 확인해야 하는 정보 | 비정상 상태의 예 | 영향받을 수 있는 기능 | 운영자의 1차 확인 |
| --- | --- | --- | --- | --- |
| Spring Boot Health | 프로세스와 Health 상태, 응답 시각, 현재 버전, 주요 의존성 상태, 마지막 정상 확인 시각 | Health 실패, 응답 없음, 반복 재시작, 의존성 상태 저하 | 거래 접수·조회, 위험 대응, 사건과 감사 이력 등 핵심 업무 전반 | 배포 버전과 변경 시각, 애플리케이션 로그, 오류율·지연시간, PostgreSQL·FastAPI 등 의존성 상태를 확인한다. |
| FastAPI Health | 프로세스와 Health 상태, 응답 시각, 모델·Rule 구성 로드 상태, 마지막 정상 확인 시각 | Timeout, Health 실패, 반복 재시작, 분석 요청 오류 급증 | Rule·ML 분석, AI 리포트와 fallback; 연동 구조에 따라 거래 분석 지연 가능 | FastAPI 로그와 자원 상태, Spring Boot→FastAPI 호출, 최근 배포, 오류 유형과 영향받은 요청 식별자를 확인한다. |
| PostgreSQL 연결 상태 | 연결 성공 여부, 응답 지연, 활성·대기 연결, Connection Pool 사용 상태, 마지막 정상 확인 시각 | 연결 거부, 쿼리 Timeout, Pool 고갈, 반복 연결 실패 | 거래·탐지·사건·감사·AI 사용량 데이터 저장과 조회 | DB 가용성, Pool 상태, 장기 실행 요청, 최근 배포와 연결 설정 변경 여부를 확인한다. |
| Redis 연결 상태 | 연결 성공 여부, 응답 지연, 캐시 읽기·쓰기 실패, 마지막 정상 확인 시각 | 연결 실패, Timeout, 오류 급증, 캐시 사용 불가 | 정확 일치 리포트 캐시와 향후 집계 데이터; External Risk는 현재 Redis를 사용하지 않음 | Redis 상태, 애플리케이션 캐시 오류와 원본 서비스 부하를 확인한다. |
| Kafka Producer·Consumer 상태 | 도입 이후 Producer 전송 결과, Consumer 실행 상태, 처리율, Consumer Lag, 재처리·중복 징후, 마지막 정상 확인 시각 | 발행 실패, Consumer 중단, Lag 증가, 반복 소비 | Kafka 도입 이후의 비동기 사건·리포트·통계 처리 | Kafka 도입 여부와 대상 흐름을 먼저 확인하고, 브로커·Producer·Consumer 상태, 오류 로그, `eventId`와 멱등 처리 결과를 확인한다. |
| External Risk Mock 상태 | 호출 성공·typed failure, 응답 지연, Provider 기준 시각, 마지막 정상 확인 시각 | Timeout, unavailable, invalid response | 독립 External Risk 조회 경계; 실패 시 현재 분석을 계속하지 않음 | 활성 profile·scenario, 민감정보 없는 `traceId`·failure category 로그와 최근 변경을 확인한다. |
| LLM Provider 호출 상태 | 모델별 성공·실패·Timeout, 응답 형식 검증, 토큰, 비용, 지연, 마지막 정상 확인 시각 | Timeout, 연결 실패, Provider 오류, 출력 형식 오류, 특정 모델 오류율 급증 | AI 사건 리포트; Rule·ML 위험 판단과 거래·사건 처리는 변경되어서는 안 됨 | 모델·오류 유형, `executionId`, 실제 `attemptId`, 관련 `aiRequestId`, 재시도와 템플릿 fallback 결과, 호출량·비용 급증 여부를 확인한다. |
| 현재 배포 버전 | 서비스별 버전, 배포 환경, 배포 시각, 변경 이력과 배포 상태 | 서비스 간 버전 불일치, 배포 직후 오류·지연 증가, 버전 식별 불가 | 변경된 서비스와 연결 기능 | 배포 전후 지표, 변경 내역, 서비스별 버전, 배포 로그와 승인된 복구 절차를 확인한다. |
| 마지막 정상 확인 시각 | 운영 대상별 마지막 성공 시각과 확인 방식 | 시각 갱신 중단, 현재 상태와 지나치게 오래된 확인 결과 | 상태 판단 신뢰도와 장애 탐지 지연 | 수집 경로와 시계 동기화 상태, 마지막 성공·첫 실패 시각, 수집 자체의 장애 여부를 확인한다. |

다음 원칙을 적용한다.

- 모든 거래에 LLM을 호출하지 않는다.
- HIGH·CRITICAL 사건을 중심으로 LLM을 호출한다.
- AI 비용은 실제 호출량, 입력·출력 토큰과 적용 가격 등 측정 가능한 사용량 데이터에 근거한다.
- 측정하지 않은 비용 절감률을 성과로 작성하지 않는다.
- 비용만 낮추지 않고 Cost, Latency, Quality를 함께 비교한다.
- 비용 급증이 위험 점수, 위험등급, 거래 대응이나 FDS 담당자의 최종 판정을 자동으로 변경해서는 안 된다.
- 생성형 AI는 위험 점수, 최종 판정, 거래 차단, 고객 제재와 사건 상태 확정을 수행하지 않는다.

## 9. 장애 시나리오별 요구사항

이 절은 운영자가 관찰하고 판단할 요구사항을 정의한다. AI 리포트 자동 재시도는 Timeout·연결 실패에 최대 1회로 확정하며, 그 외 의존성의 구체적인 자동 복구·재시도 횟수, Circuit Breaker 설정과 배포 복구 구현은 후속 문서에서 확정한다.

### 9.1 FastAPI Timeout

#### 현상

Spring Boot에서 FastAPI 분석 요청의 응답을 정해진 시간 안에 받지 못하거나 분석 대기 요청이 증가한다.

#### 탐지 정보

Spring Boot·FastAPI 로그, 호출 지연·Timeout·처리량, 서비스 Health, 자원 상태와 `transactionId`, `caseId`, `traceId`를 확인한다. 정확한 Timeout 기준은 `TBD`이다.

#### 영향 범위

Rule·ML 탐지와 후속 사건 생성이 지연될 수 있다. 거래 접수 데이터의 보존과 상태 정합성은 Spring Boot가 유지해야 한다.

#### 업무 지속 원칙

Rule 분석 시작 commit 뒤 FastAPI Timeout·분석·결과 채택에 실패하면 거래를
`ANALYZING → FAILED`로, 해당 DetectionResult를 `FAILED`로 같은 쓰기 경계에서
확정한다. 응답이 없다는 이유로 위험정보가 없거나 거래가 정상이라고 간주하지
않는다. 실패 후 재분석·수동 복구는 별도 승인 범위이다.

#### 운영자 행동

FastAPI Health·자원·최근 배포를 확인하고, 특정 요청·모델·Rule에 집중된 문제인지 구분한다. Spring Boot의 대기·실패 상태와 중복 재요청 가능성을 확인하고 승인된 임시 대응만 수행한다.

#### 기록 항목

첫 발생·종료 시각, 영향 요청과 기능, 관련 버전·식별자, Timeout 분포, 임시 대응, 원인, 구조적 해결과 재발 방지를 기록한다.

### 9.2 External Risk Mock Timeout

#### 현상

외부 위험정보 조회가 지연되거나 `TIMEOUT` typed failure로 종료된다.

#### 탐지 정보

External Risk Mock 상태, 호출 지연·Timeout, `traceId`와 failure category를 확인한다.

#### 영향 범위

현재 독립 조회 경계는 실패 시 성공 Snapshot을 만들지 않고 분석을 계속하지 않는다.
목표 거래 연결에서는 거래가 `RECEIVED`를 유지하고 DetectionResult와
DetectionEvidence를 생성하지 않으며 FastAPI·위험 대응 최종화·성공 Snapshot v2를
호출하거나 생성하지 않는다. 멱등 레코드는 실패를 확정하고 같은 요청 재생에서는
External Risk Provider를 다시 호출하지 않는다. 이 거래 연결은 아직 구현되지 않았다.

#### 업무 지속 원칙

조회 실패를 위험정보 없음이나 `UNMATCHED`로 해석하지 않는다. 자동 retry, cache,
stale data와 fallback 없이 typed failure를 전파한다. 향후 cache·Circuit Breaker·fallback은
별도 Issue와 계약 승인이 필요하다.

`ANALYZING → FAILED`와 DetectionResult `FAILED`는 External Risk 성공 뒤 Rule 분석
시작 commit이 완료된 후 발생한 Rule 분석·FastAPI·결과 채택 실패에만 적용한다.
External Risk 선행 조회 실패를 이 상태 전이로 변환하지 않는다.

#### 운영자 행동

Mock 활성 profile·property와 scenario, 성공·failure category를 구분한다. 복구 후 재조회는 별도 승인된 실행 경로 없이 자동 수행하지 않는다.

#### 기록 항목

장애 시각, 안전한 trace, failure category, 임시 대응, 원인과 재발 방지를 기록한다. 고객·계좌·기기 reference와 Provider 원문은 로그에 기록하지 않는다.

### 9.3 LLM Timeout

#### 현상

AI 리포트 모델 호출이 제한 시간 안에 완료되지 않고 생성 지연과 템플릿 fallback이 증가한다.

#### 탐지 정보

모델별 지연·Timeout, 토큰, 호출 단계, `caseId`, `aiRequestId`, `executionId`, 실제 `attemptId`, `traceId`와 fallback 결과를 확인한다.

#### 영향 범위

AI 사건 리포트만 지연·실패할 수 있으며 Rule·ML 위험 판단, 거래 대응과 사건 생성 결과는 변경되지 않는다.

#### 업무 지속 원칙

같은 `executionId`에서 최대 한 번 자동 재시도한 뒤 정상 결과가 없으면 Rule·ML 결과 기반 템플릿 리포트로 fallback한다. AI 리포트 생성은 핵심 거래 판단의 필수 경로가 아니다.

#### 운영자 행동

Provider·모델별 상태와 호출량, 네트워크, 입력 크기, 재시도 여부를 확인한다. 중복 재생성으로 비용이 증가하지 않는지 확인한다.

#### 기록 항목

Timeout 시각, 모델, 지연, 관련 사건·요청, 재시도, fallback, 비용 영향, 원인과 후속 조치를 기록한다.

### 9.4 LLM Provider 오류

#### 현상

Provider가 오류 응답을 반환하거나 인증·할당량·서비스 문제로 모델 호출이 실패한다.

#### 탐지 정보

Provider 상태, 오류 유형·응답 코드, 모델별 오류율, 호출량·비용과 `caseId`, `aiRequestId`, `executionId`, 실제 `attemptId`, `traceId`를 확인한다. 민감한 인증정보는 로그에 기록하지 않는다.

#### 영향 범위

AI 사건 리포트 생성과 재생성에 영향을 주며 핵심 거래·탐지·사건 처리는 분리되어야 한다.

#### 업무 지속 원칙

비일시적 Provider 오류는 자동 재시도하지 않고 템플릿 fallback을 사용하며 위험 판단 결과를 변경하지 않는다. 다른 모델 전환 여부와 조건은 별도 사용자 승인 정책으로 결정한다.

#### 운영자 행동

오류가 전체 Provider, 특정 모델, 배포 버전 또는 자격 설정에 한정되는지 확인한다. 승인된 fallback 상태와 비용 집계 누락 여부를 점검한다.

#### 기록 항목

오류 시작·종료 시각, 모델·오류 유형, 영향 사건, fallback, 비용·품질 영향, 임시 대응, 원인과 재발 방지를 기록한다.

### 9.5 LLM 출력 형식 오류

#### 현상

LLM 응답이 승인된 구조 또는 필수 항목 검증을 통과하지 못해 리포트를 사용할 수 없다.

#### 탐지 정보

검증 실패 유형, 프롬프트·모델 버전, fallback 결과와 `caseId`, `aiRequestId`, `executionId`, 실제 `attemptId`, `traceId`를 확인한다. 민감한 원문 입력·출력의 무분별한 기록은 금지한다.

#### 영향 범위

AI 리포트 품질과 준비 시간에 영향을 주며 Rule·ML 위험 판단에는 영향을 주지 않는다.

#### 업무 지속 원칙

출력 형식 검증 실패는 자동 재시도하지 않고 템플릿 리포트로 fallback한다. 형식 오류 응답을 정상 리포트로 표시하지 않는다.

#### 운영자 행동

특정 모델·프롬프트 버전에 집중되는지 확인하고 품질 통과율과 fallback 이전 실제 호출 비용을 비교한다.

#### 기록 항목

실패 시각, 검증 항목, 모델·프롬프트 버전, 재시도·fallback, 영향 사건, 비용과 구조적 해결을 기록한다.

### 9.6 Redis 장애

#### 현상

Redis 연결·읽기·쓰기 오류가 증가하고 정확 일치 AI 리포트 캐시를 사용할 수 없다.

#### 탐지 정보

Redis Health·지연·오류, 애플리케이션 캐시 로그, 원본 서비스 호출량, `caseId`, `transactionId`, `traceId`와 캐시 사용 여부를 확인한다.

#### 영향 범위

동일 사건 리포트의 중복 호출 가능성과 향후 집계 기능 지연이 발생할 수 있다. External Risk 독립 경계는 현재 Redis를 사용하지 않는다. PostgreSQL의 핵심 업무 데이터와 구분한다.

#### 업무 지속 원칙

캐시 미사용 또는 제한된 fallback 가능성을 검토한다. 캐시 장애 때문에 다른 사건의 리포트를 재사용하거나 조회 실패를 정상으로 간주해서는 안 된다.

#### 운영자 행동

Redis 상태와 영향받은 캐시 종류를 확인하고 원본 서비스·LLM 부하와 비용 급증을 함께 감시한다. 승인된 캐시 우회 정책만 적용한다.

#### 기록 항목

장애 시각, 영향 캐시와 기능, 원본 호출·비용 변화, 임시 대응, 데이터 정합성 확인, 원인과 재발 방지를 기록한다.

### 9.7 Kafka Consumer 중단

#### 현상

Kafka 도입 이후 Consumer 처리가 멈추고 Consumer Lag과 비동기 작업 대기가 증가한다.

#### 탐지 정보

Consumer 상태·처리량·Lag, 오류 로그, 재시작 이력, `eventId`, `caseId`, `aiRequestId`, `traceId`와 중복 처리 결과를 확인한다.

#### 영향 범위

Kafka 도입 이후 비동기로 분리된 사건·AI 리포트·통계 처리에 한정해 판단한다. 동기 핵심 거래 판단이 Kafka에 의존하도록 임의로 확대하지 않는다.

#### 업무 지속 원칙

핵심 거래·탐지 결과는 유지하고 비동기 작업을 적체 상태로 구분한다. 재처리 시 멱등성을 보장해야 하며 구체적인 복구 절차는 `TBD`이다.

#### 운영자 행동

Kafka 도입 여부와 해당 Consumer 책임을 먼저 확인한다. 중단 원인, 마지막 성공 이벤트, 적체 범위와 중복 가능성을 확인하고 승인된 재개 절차를 수행한다.

#### 기록 항목

중단·재개 시각, Consumer와 대상 흐름, 최대·해소 Lag, 영향 이벤트, 중복·누락 검증, 임시 대응과 재발 방지를 기록한다.

### 9.8 DB Connection Pool 고갈

#### 현상

DB 연결 획득 대기와 Timeout이 증가하고 활성 연결이 지속적으로 사용되어 신규 요청이 처리되지 않는다.

#### 탐지 정보

Pool 활성·유휴·대기 상태, 연결 획득 지연, 장기 실행 요청, DB 상태, API 오류·지연과 `transactionId`, `caseId`, `traceId`를 확인한다.

#### 영향 범위

거래 접수·조회, 탐지 결과·사건·감사 이력과 AI 사용량 저장 등 PostgreSQL 사용 기능 전반에 영향을 줄 수 있다.

#### 업무 지속 원칙

데이터 저장 성공 여부가 불명확한 요청을 임의로 성공 처리하지 않는다. 거래·사건 정합성과 중복 요청 방지를 우선한다.

#### 운영자 행동

DB 가용성, 장기 트랜잭션·쿼리, 최근 배포, 요청 급증과 연결 누수를 확인한다. 승인된 부하 제한·복구 절차를 적용하고 데이터 누락·중복을 검증한다.

#### 기록 항목

고갈 시작·종료 시각, Pool 상태, 영향 요청·기능, 실패·재시도 결과, 임시 대응, 원인과 구조적 해결을 기록한다.

### 9.9 중복 이벤트

#### 현상

Kafka 도입 이후 동일 이벤트가 반복 소비되거나 같은 사건·AI 리포트·사용량 기록이 중복 생성될 징후가 나타난다.

#### 탐지 정보

`eventId`, `transactionId`, `caseId`, `aiRequestId`, 처리 시각, Producer·Consumer 로그와 멱등 처리 결과를 확인한다.

#### 영향 범위

비동기 사건·리포트·통계와 비용 집계의 중복 가능성이 있다. 이미 확정된 거래 판단을 중복 이벤트가 변경해서는 안 된다.

#### 업무 지속 원칙

중복 이벤트를 식별하고 승인된 멱등 처리 결과를 유지한다. 중복 여부가 불명확한 경우 새 사건이나 새 비용 기록을 임의로 확정하지 않는다.

#### 운영자 행동

발행 중복과 소비 재처리를 구분하고 동일 식별자의 결과를 대조한다. 사건·리포트·비용 데이터의 중복 여부와 보정 필요성을 사용자에게 보고한다.

#### 기록 항목

중복 발생 시각, 이벤트 식별자, 발생 경로, 영향 데이터, 차단·보정 결과, 원인과 재발 방지를 기록한다.

### 9.10 AI 호출 비용 급증

#### 현상

거래량이나 사건량 변화로 설명되지 않는 호출량·토큰·사건당 비용·거래 1,000건당 비용 증가가 나타난다.

#### 탐지 정보

모델별 호출량, 입력·출력 토큰, 재시도·재생성, 라우팅 비율, 캐시 적중률, fallback, `caseId`, `aiRequestId`, distinct `executionId`·`attemptId`와 가격 기준을 확인한다.

#### 영향 범위

AI 운영 예산과 리포트 생성 기능에 영향을 주지만 위험 점수, 위험등급, 거래 대응과 최종 판정은 자동 변경하지 않는다.

#### 업무 지속 원칙

비용 급증을 금융 위험 신호로 해석하지 않는다. 승인된 비용 정책 안에서 원인을 확인하고 호출 제한·모델 정책 변경은 사용자 결정에 따른다.

#### 운영자 행동

트래픽 증가, 재시도 루프, 캐시 장애, 재생성 폭증, 모델 라우팅 쏠림과 가격 기준 변경을 구분한다. 측정 데이터 없이 절감 효과를 주장하지 않는다.

#### 기록 항목

급증 시각·기간, 기준 대비 사용량과 비용, 모델·원인, 영향 사건, 임시 대응, 승인 사항과 후속 FinOps 실험을 기록한다.

### 9.11 특정 모델 오류율 급증

#### 현상

특정 모델에서 Timeout, Provider 오류 또는 형식·품질 검증 실패 비율이 증가한다.

#### 탐지 정보

모델·버전별 호출량, 오류 유형, 지연, 토큰, 품질 통과율, 라우팅 사유와 `aiRequestId`, `executionId`, 실제 `attemptId`, `caseId`, `traceId`를 확인한다.

#### 영향 범위

해당 모델로 라우팅된 AI 리포트의 지연·품질·비용에 영향을 준다. Rule·ML 탐지 결과에는 영향을 주지 않는다.

#### 업무 지속 원칙

승인된 정책에 따라 재시도 또는 템플릿 fallback을 사용한다. 모델 라우팅 변경은 비용·품질과 사용자 승인을 함께 고려한다.

#### 운영자 행동

전체 Provider 장애와 모델 한정 장애를 구분하고 최근 모델·프롬프트·라우팅 변경을 확인한다. 다른 모델과 오류·비용·품질을 비교한다.

#### 기록 항목

오류 증가 시각, 모델·버전, 오류 유형, 영향 사건, fallback·비용·품질, 임시 대응과 구조적 해결을 기록한다.

### 9.12 배포 후 지연시간 또는 오류율 증가

#### 현상

특정 서비스 배포 직후 API·Rule·ML·LLM 지연시간 또는 오류율이 증가하고 처리량이 감소한다.

#### 탐지 정보

배포 버전·시각·변경 내역, 배포 전후 지연·오류·처리량, 서비스 Health, 의존성 상태와 `traceId`, `transactionId`, `caseId`, `aiRequestId`, 필요한 경우 `executionId`를 확인한다.

#### 영향 범위

변경된 서비스와 의존 흐름에 따라 거래 접수, 탐지, 사건 또는 AI 리포트가 영향을 받을 수 있다.

#### 업무 지속 원칙

영향 기능을 구분하고 핵심 거래·사건 정합성을 우선한다. 복구·롤백 조건과 방식은 배포 정책에서 `TBD`로 확정한다.

#### 운영자 행동

배포 전후 같은 조건의 지표를 비교하고 버전 불일치와 설정 변경을 확인한다. 승인된 배포 복구 절차를 수행하고 복구 후 지표와 데이터 정합성을 검증한다.

#### 기록 항목

배포·이상 탐지·복구 시각, 버전과 변경 내역, 영향 서비스·기능, 판단 근거, 임시 대응, 원인, 구조적 해결과 재발 방지를 기록한다.

## 10. 핵심 기능과 부가 기능의 장애 경계

- LLM 실패가 Rule·ML 위험 판단 결과를 변경하지 않는다.
- AI 리포트 실패는 거래 접수·탐지·사건 처리 실패와 구분한다.
- 생성형 AI는 위험 점수, 최종 판정, 거래 차단, 고객 제재와 사건 상태 확정을 수행하지 않는다.
- 외부 위험정보 timeout·unavailable·invalid response는 위험정보 없음이나
  `UNMATCHED`로 바꾸지 않고 typed failure로 전파하며 현재 분석을 계속하지 않는다.
  목표 거래 연결에서는 거래 `RECEIVED` 유지, DetectionResult·Evidence 미생성,
  FastAPI·최종화 미호출과 멱등 실패 확정을 적용한다. 같은 요청 재생은 Provider를
  다시 호출하지 않는다. Rule 분석 시작 commit 이후의 `ANALYZING → FAILED` 및
  DetectionResult `FAILED` 경계와 구분한다.
- Redis 장애가 발생해도 캐시 미사용 또는 제한된 fallback 가능성을 검토한다. 정확 일치 조건을 우회하거나 다른 사건의 AI 리포트를 재사용하지 않는다.
- Kafka 장애는 Kafka 도입 이후의 비동기 사건·리포트·통계 작업에 한정하여 영향 범위를 판단한다.
- Spring Boot는 거래·사건 상태와 업무 정합성의 최종 소유자이다. 핵심 데이터의 저장 결과가 불명확하면 임의로 성공 처리하지 않는다.
- Rule 분석 시작 commit 이후 FastAPI·분석·채택 실패는 거래
  `ANALYZING → FAILED`와 DetectionResult `FAILED` 경계로 확정한다. 실패 후
  재분석·수동 복구 정책은 후속 사용자 결정 사항이다.

## 11. 운영 알림 요구사항

알림은 운영자가 영향 범위를 판단하고 1차 확인을 시작할 수 있는 정보와 연결되어야 한다. 구체적인 수치, 지속 시간, 심각도와 알림 채널은 이번 문서에서 확정하지 않고 `TBD`로 둔다.

| 알림 후보 | 운영자가 함께 확인할 정보 |
| --- | --- |
| 서비스 Health 실패 | 서비스·환경·버전, 최초 실패·마지막 정상 시각, 의존성 상태와 영향 기능 |
| 오류율 급증 | 서비스·요청 유형·오류 유형·버전, 처리량과 관련 식별자 |
| 지연시간 증가 | 서비스·요청 단계·백분위 `TBD`, Timeout과 처리량 변화 |
| DB Connection Pool 고갈 위험 | 활성·유휴·대기 연결, 연결 획득 지연, 장기 실행 요청과 DB 상태 |
| Kafka Consumer Lag 증가 | Kafka 도입 이후 Consumer·대상 흐름, Lag·처리량·마지막 성공 이벤트 |
| LLM Timeout 또는 오류 급증 | Provider·모델·버전, 오류 유형, 영향 사건, 재시도와 fallback |
| fallback 비율 증가 | 원인별 fallback, 모델·Provider 상태, 품질·지연과 영향 사건 |
| AI 호출 비용 급증 | 모델별 호출·토큰·비용, 거래량·사건량, 재시도·캐시·라우팅 변화 |
| 배포 후 이상 징후 | 배포 버전·시각, 변경 서비스, 배포 전후 오류·지연·처리량과 Health |

알림 중복 억제, 연관 알림 묶음, 해제 조건, 담당자 라우팅과 채널은 `TBD`이다. 비용 알림이 위험 판단 결과를 자동 변경하거나 기술 알림이 FDS 사건 최종 판정을 대신해서는 안 된다.

## 12. 운영 이력 요구사항

운영 이력에는 다음 정보를 기록할 필요가 있다.

- 장애 발생·탐지·종료 시각
- 영향받은 서비스와 거래 접수·탐지·사건·AI 리포트 기능
- 관련 배포 버전과 변경 내역
- 장애 판단에 사용한 로그·메트릭·트레이스 또는 탐지 지표
- 임시 대응과 수행 시각
- 확인된 원인과 아직 확인되지 않은 가설의 구분
- 구조적 해결과 재발 방지 항목
- 담당자와 승인자
- 관련 `traceId`, `transactionId`, `caseId`, `aiRequestId`, `executionId`, 필요한 경우 `attemptId`와 Kafka 도입 이후 `eventId`
- 복구 후 서비스 상태와 데이터 정합성 검증 결과
- AI 호출량·토큰·비용·품질에 미친 영향

운영 이력은 변경 전후와 판단 근거를 감사 가능하게 남겨야 한다. 별도의 `ServiceIncident` 또는 `DeploymentRecord` Entity 도입, 저장 위치, 데이터 구조, 보존 기간과 API는 이번 문서에서 확정하지 않으며 `TBD`이다.

## 13. 화면과 도구의 책임 경계

### React 관리자 화면

React 관리자 화면은 운영자가 업무 영향과 조치 상태를 빠르게 판단하는 데 필요한 정보를 제공한다.

- 서비스 상태 요약과 마지막 정상 확인 시각
- 서비스별 현재 배포 버전과 변경 이력
- 모델별 AI 호출량·입력 토큰·출력 토큰·비용 요약
- 정확 일치 캐시, 템플릿 fallback과 장애 이력 요약
- 거래 접수·탐지·사건·AI 리포트 중 영향받은 업무 상태
- 승인된 운영 정책, 임시 대응과 후속 조치 이력
- 관련 기술 상세 화면 또는 Grafana 탐색 경로

React 관리자 화면은 FDS 분석 담당자의 사건 최종 판정 화면과 플랫폼 운영자의 장애 대응 화면을 역할별로 구분해야 한다.

### Grafana

Grafana는 Observability Stack 도입 이후 기술 메트릭의 상세 분석을 담당한다.

- 기술 메트릭의 시계열 분석
- 서비스별 API·Rule·ML·LLM 지연시간
- 오류율과 처리량
- DB Connection Pool
- Kafka 도입 이후 Consumer Lag
- 런타임과 인프라 상세 상태
- 배포 전후 기술 지표 비교

React에서 Grafana와 동일한 기술 대시보드를 전부 다시 구현하지 않는다. React는 업무 영향과 운영 조치 요약에 집중하고, Grafana는 기술 원인 분석을 위한 상세 시계열에 집중한다. 구체적인 화면 구성과 연동 방식은 플랫폼 운영 화면 와이어프레임에서 확정한다.
