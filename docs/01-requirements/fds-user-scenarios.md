# FDS 핵심 이상거래 사용자 시나리오

## 1. 문서 목적

이 문서는 `docs/00-overview/fds-service-scope.md`에서 확정한 FDS 서비스 범위와 8개의 핵심 이상거래 시나리오를 화면, ERD와 API 설계의 입력으로 사용할 수 있도록 상세화한다.

이 문서에서는 요구사항과 업무 흐름을 정의한다. Rule v1의 R001~R004 조건, 점수와 위험등급 초기 실험값은 [`rule-v1-detection-contract.md`](./rule-v1-detection-contract.md)를 단일 기준으로 사용한다. 그 밖의 Rule·ML 통합, 성능 목표, API 요청·응답과 데이터베이스 구조는 이 문서에서 확정하지 않는다.

> 본 문서는 FinGuardOps의 금융 FDS 도메인 요구사항을 정의한다.
> 배포, Observability, 장애 대응과 AI 비용 관리는 별도의
> 플랫폼 운영 요구사항 및 아키텍처 문서에서 정의한다.

## 2. 공통 원칙

- 분석 대상은 계좌이체, 오픈뱅킹 거래, ATM 현금 인출과 거래 전후 사용자 행동으로 한정한다.
- Rule과 ML은 위험 점수, 탐지 근거와 위험등급 산출을 담당한다.
- 생성형 AI는 위험 점수 계산이나 최종 판정을 수행하지 않는다.
- 거래 대응 정책과 거래 상태의 최종 변경은 백엔드가 담당하고, 최종 정상·오탐·이상거래 판정은 FDS 담당자가 수행한다.
- 외부 금융기관 연동, 실제 본인인증, 실제 거래 차단과 실제 대출 실행은 목표
  시나리오의 Mock 후보다. External Risk는 현재 독립 Port·Policy Service,
  local/dev/test 결정적 Mock과 성공 Snapshot을 Rule v2에 전달하는 내부
  per-invocation coordinator까지 구현되어 있다.
- 아래의 위험등급은 시나리오별 탐지 신호를 설명하기 위한 예상 범위이다. 실제 등급은 승인된 점수 통합 정책과 검증 결과에 따라 결정한다.
- Rule v1은 거래 접수 시 현재 거래의 `occurredAt`을 기준으로 평가하며, 행동 이벤트 접수만으로 자동 재평가하지 않는다.
- Rule v1 계약, DetectionResult·Evidence 물리 모델, 현재
  `POST /api/v1/rule-analysis`와 내부 결과 생성·검증·채택은 구현되었다. 거래
  접수 연결은 미구현이지만 External Risk를 필수 입력으로 검증하는 FastAPI
  `POST /api/v2/rule-analysis` wire와 이를 exact wire로 호출하는 Backend Java v2
  DTO·mapper·Client·내부 오케스트레이션 경계는 구현되었다.

### 외부 위험정보 서비스 장애 처리 정책

- 성공 응답의 빈 match는 `UNMATCHED`, 하나 이상의 허용 match는 `MATCHED`다.
- timeout·unavailable·invalid response는 분석을 계속하지 않고 typed exception으로
  전파한다. 실패를 위험정보 없음, 정상 결과 또는 `UNMATCHED`로 변환하지 않는다.
- 현재 자동 retry, cache, stale data, fallback과 Circuit Breaker는 없다.
- 목표 거래 접수 연결에서는 External Risk 실패 시 거래가 `RECEIVED`를 유지하고
  DetectionResult를 생성하지 않으며 FastAPI와 위험 대응 최종화를 호출하지 않는다.
  멱등 실패 재생은 Provider를 다시 호출하지 않는다. timeout은 `DEPENDENCY_TIMEOUT`, unavailable은
  `DEPENDENCY_UNAVAILABLE`, 그 밖의 계약·검증·변환 오류는 `INTERNAL_ERROR`에
  매핑한다. 거래 연결과 공개 HTTP 오류 매핑은 아직 구현되지 않았다.
- cache·Circuit Breaker·fallback은 향후 별도 Issue·ADR 승인이 필요한 운영
  고도화 후보이며 현재 운영 경계에 적용되지 않는다.

현재 External Risk Mock은 송신 계좌, 수신 계좌와 기기 scenario만 지원한다.
IP reference와 IP 조회는 현재 거래 모델에 없고 피싱 정책도 미구현이다. 아래의
위험 IP·피싱·외부 위험 점수·등급·대응 표현은 최종 사용자 시나리오 또는 향후
확장 후보이며 현재 구현 동작을 의미하지 않는다. FastAPI v2
`RuleAnalysisRequestV2`와 검증 Endpoint, Backend Java v2 DTO·mapper·직접 Client·
내부 오케스트레이션 경계와 Mock 성공 Snapshot을 전달하는 coordinator는 구현됐지만
실제 외부 HTTP Provider와 public 거래 접수 상위 오케스트레이션은 아직 구현되지
않았다. coordinator 직접 재호출·멱등 경계 밖 동시 호출은 Provider를 다시 호출할 수
있으며 자동 retry·fallback·cache와 멱등 실패 재생은 없다.
`ExternalRiskSnapshot` 영속화는 이번 목표가 아니며 별도 승인 대상이다.

### AI 리포트 생성 실패 처리 정책

- LLM은 HIGH·CRITICAL 사건의 리포트 생성에만 사용한다.
- AI 리포트 생성은 거래 승인과 위험판단의 필수 경로에서 분리한다.
- 생성에 실패하면 Rule·ML 결과 기반 템플릿 리포트를 생성한다.
- 리포트 실패가 거래 대응과 사건 생성을 되돌리지 않는다.
- 실패 원인과 Fallback 여부를 기록한다.

### 사건 처리 상태와 최종 판정

사건 처리 상태는 조사 진행 단계를 나타낸다.

- `OPEN`: 사건이 생성되어 검토를 기다리는 상태
- `IN_REVIEW`: 담당자가 사건을 검토하고 있는 상태
- `ADDITIONAL_INFORMATION_REQUIRED`: 현재 정보만으로 판정할 수 없어 추가 정보가 필요한 상태
- `CLOSED`: 조사와 필요한 후속 기록이 완료되어 사건 처리를 종료한 상태

최종 판정은 조사 결과를 나타낸다.

- `NORMAL`: 조사 결과 정상적인 금융거래로 확인
- `FALSE_POSITIVE`: Rule 또는 모델의 부정확한 경보로 확인되어 탐지 정책 개선 대상으로 기록
- `CONFIRMED_FRAUD`: 조사 결과 이상거래로 확정

현재 정보만으로 판정할 수 없는 경우에는 새로운 최종 판정을 만들지 않고 사건 처리 상태를 `ADDITIONAL_INFORMATION_REQUIRED` 또는 `IN_REVIEW`로 유지한다.

### 후속 설계에서 확정할 항목

이 문서는 요구사항과 업무 흐름을 정의한다. Rule v1의 점수·위험등급 초기 실험값은 전용 계약 문서에서 확정한다. External Risk retry·cache·Circuit Breaker·fallback은 현재 적용하지 않으며 별도 Issue·ADR 승인 전에는 후속 후보일 뿐이다. Rule v1 이후 점수 통합, Kafka 세부 구조와 ML 성능 목표도 추가 결정 사항 또는 후속 아키텍처 문서에서 정의한다.

## 3. FDS-SCN-001 신규 기기에서 고액 이체

### 목적

평소 사용하지 않던 기기에서 로그인한 뒤 최초 수취인에게 평소보다 현저히 큰 금액을 이체하는 계정 탈취 의심 흐름을 탐지한다.

### 주요 행위자

- 이체를 요청하는 고객
- 거래 및 탐지 흐름을 처리하는 FDS 시스템
- 사건을 검토하는 FDS 담당자
- 현재 계좌·기기 scenario와 향후 위험 IP 목표를 구분하는 외부 위험정보 Mock 경계

### 사전 조건

- 고객과 출금 계좌가 등록되어 있다.
- 고객의 기존 기기, 수취인과 거래 이력을 비교할 수 있다.
- 현재 기기가 고객의 기존 사용 기기인지 판단할 수 있다.
- 고객의 평소 이체 금액을 비교할 수 있는 거래 이력이 있거나, 이력이 부족함을 별도로 표시할 수 있다.

### 분석 트리거

- 실시간 거래 요청: 고액 이체 요청 시 현재 거래와 고객 기준선을 분석한다.
- 행동 이벤트 발생: 신규 기기 로그인·등록 또는 신규 수취인 등록 시 후속 거래 관찰을 시작한다.
- 외부 위험정보 갱신: 관련 기기·수취 계좌의 위험정보 갱신과 향후 IP 확장이
  영속·사건 경계에 연결되면 열린 사건의 근거를 보완하는 목표 흐름이다.
### 정상 비교 흐름

1. 고객이 기존에 사용하던 신뢰 기기에서 로그인한다.
2. 고객이 이전에 거래한 수취 계좌로 평소 범위의 금액을 이체한다.
3. Rule·ML 분석 결과에 따라 거래가 승인되거나 모니터링 대상으로 기록된다.
4. 사건 생성 조건을 충족하지 않으면 별도 사건을 만들지 않는다.

### 발생한 금융거래

- 거래 유형: 계좌이체
- 출금 주체: 로그인한 고객의 계좌
- 수취 주체: 고객에게 최초인 수취 계좌
- 금액 특성: 고객의 평소 평균 이체 금액보다 현저히 큰 금액이며, 기준 문서의 대표 흐름은 평균의 10배 금액이다.
- 구현 시 실제 금액 자체보다 고객별 평소 금액과의 비율을 함께 판단한다.

### 거래 전후 행동 이벤트

```text
LOGIN 또는 DEVICE_REGISTERED
→ BENEFICIARY_REGISTERED
→ TRANSFER_REQUESTED
```

- 거래 전: 신규 기기 로그인 또는 등록, 최초 수취인 등록
- 거래 시점: 고액 이체 요청
- 거래 후: 추가 인증 결과, 거래 상태 변경, 동일 기기의 후속 거래를 관찰한다.

### 필요한 데이터

- 고객 식별 정보와 계좌 식별 정보
- 거래 식별 정보, 거래 시각, 금액, 출금·수취 계좌
- 기기 식별 정보, 신규 기기 여부와 기기 신뢰등급
- 로그인 IP, 접속 지역과 해외 IP 여부
- 고객별 과거 이체 금액의 집계값
- 수취 계좌의 최초 거래 여부와 등록 시각
- 악성 앱·원격제어 앱·앱 위변조 Mock 신호
- 현재 외부 위험계좌·위험 기기 결과와 조회 상태. 위험 IP는 향후 후보

### 적용 가능한 Rule

- 신규 기기에서 거래
- 고객 평균 거래 금액 대비 비정상적으로 큰 이체
- 최초 수취 계좌로 이체
- 새벽 시간대 거래
- 해외 IP 접속
- 악성 앱 또는 원격제어 앱 탐지 Mock 신호
- 현재 외부 위험계좌·위험 기기 일치. 위험 IP 일치는 향후 후보

Rule별 점수와 조합 가중치는 이 문서에서 확정하지 않는다.

Rule v1에서 이 시나리오와 직접 연결되는 Baseline은 R001, R002와 R004이다. R002는 실제 신규 기기·신뢰도를 판단하지 않고 최근 `DEVICE_REGISTERED` 이벤트 존재만 사용하며, R004도 실제 최초 수취인 여부가 아니라 최근 `BENEFICIARY_REGISTERED` 이벤트 존재만 사용한다. 정확한 조건과 점수는 [Rule v1 탐지 계약](./rule-v1-detection-contract.md)을 따른다.

### ML이 사용할 수 있는 Feature

- 현재 거래 금액
- 평균 대비 거래 금액 비율
- 신규 기기 여부와 기기 신뢰등급
- 신규 수취 계좌 여부
- 수취인 등록 후 이체까지의 경과 시간
- 거래 시간대와 해외 IP 여부
- 최근 로그인 실패 횟수
- 최근 10분 거래 횟수와 최근 24시간 거래 금액
- 기기 보안 Mock 신호
- 외부 위험정보의 일치 여부와 조회 가능 여부

### 예상 위험등급

- 신규 기기와 고액 이체만 확인되면 MEDIUM 이상 후보로 분석한다.
- 최초 수취인, 위험 IP·기기·계좌 또는 보안 위험 신호가 함께 확인되면 HIGH·CRITICAL 후보가 될 수 있다.
- 예상 등급은 확정 판정이 아니며 최종 점수 통합 정책에 따른다.

### 시스템 자동 대응

- LOW이면 Mock 거래 승인 상태를 적용한다.
- MEDIUM이면 Mock 거래 승인 후 모니터링 대상으로 등록한다.
- HIGH이면 Mock 추가 인증을 요구하고 사건을 생성한다.
- CRITICAL이면 Mock 거래 보류 상태를 적용하고 긴급 사건 생성과 담당자 알림을 수행한다.
- 모든 분석 근거, 대응과 상태 변경을 감사 이력에 남긴다.

### 사건 생성 조건

- 최종 위험등급이 HIGH 또는 CRITICAL인 경우 사건을 생성한다.
- 동일 고객·기기·수취 계좌의 연속 거래가 하나의 의심 흐름이면 중복 사건 대신 기존 사건에 연관 거래로 연결할 수 있다.
- 사건에는 신규 기기, 금액 비율, 최초 수취인과 외부 위험정보를 대표 탐지 근거로 남긴다.

### 담당자 확인 항목

- 신규 기기가 고객이 실제 등록하거나 사용한 기기인지
- 로그인 IP와 지역이 고객의 평소 이용 패턴과 일치하는지
- 수취 계좌가 고객과 정상적인 거래 관계인지
- 금액 증가를 설명할 정상 목적이 있는지
- 추가 인증 성공 여부와 Mock 인증 결과
- 동일 기기·IP·수취 계좌와 연결된 다른 고객 또는 사건이 있는지
- 보안 위험 신호와 외부 위험정보의 조회 시각·신뢰 상태

### 최종 처리 예시

- 고객이 새 휴대전화 등록과 수취인·이체 목적을 확인하고 추가 인증에 성공한 경우 `NORMAL` 또는 `FALSE_POSITIVE`로 판정한 뒤 사건을 종료한다.
- 고객이 기기와 이체 요청을 부인하고 위험 수취 계좌 연계가 확인된 경우 `CONFIRMED_FRAUD`로 판정하고 Mock 후속 조치와 조사 근거를 기록한다.

### 아직 추가 결정이 필요한 사항

- 신규 기기로 판단하는 등록·사용 이력 기준
- 고객 평균 거래 금액의 산정 기간과 이력이 부족한 고객의 처리 방식
- 최초 수취인 판단 기간
- Rule v1 이후 고객 기준선·실제 기기 신뢰도·실제 최초 수취인 판단을 추가할 Rule과 점수 통합 방식
- 추가 인증 성공·실패 후 허용할 상태 전이
- 외부 위험정보 조회 실패를 위험도에 반영하는 정책

## 4. FDS-SCN-002 비밀번호 및 이체 한도 변경 후 고액 송금

### 목적

비밀번호 변경과 이체 한도 상향 직후 고액 송금이 이어지는 계정 탈취 또는 사회공학적 사기 의심 흐름을 탐지한다.

### 주요 행위자

- 보안정보와 이체 한도를 변경하고 송금을 요청하는 고객
- 거래 및 행동 이벤트를 분석하는 FDS 시스템
- 사건을 검토하는 FDS 담당자
- 외부 위험정보 Mock 서비스

### 사전 조건

- 고객의 비밀번호 변경, 이체 한도 변경과 이체 요청 이벤트를 시간 순서로 연결할 수 있다.
- 변경 전후의 이체 한도와 고객의 과거 거래 패턴을 비교할 수 있다.
- 실제 비밀번호 값은 저장하거나 분석 데이터로 사용하지 않고 변경 사실과 시각만 사용한다.

### 분석 트리거

- 행동 이벤트 발생: 비밀번호 변경, 이체 한도 변경 또는 신규 수취인 등록 시 후속 거래 관찰을 시작한다.
- 실시간 거래 요청: 관찰 중인 고객의 고액 송금 요청 시 행동 시퀀스와 거래를 함께 분석한다.
- 외부 위험정보 갱신: 관련 기기·수취 계좌의 위험정보 갱신과 향후 IP 확장이
  영속·사건 경계에 연결되면 열린 사건의 근거를 보완하는 목표 흐름이다.
### 정상 비교 흐름

1. 고객이 정상적인 본인확인 절차를 거쳐 비밀번호 또는 이체 한도를 변경한다.
2. 변경 직후 고액 거래를 수행하지 않거나, 거래 요청 시 추가 인증을 정상적으로 완료한다.
3. 시스템은 변경 이벤트와 거래를 분석하고 승인된 정책에 따라 승인 또는 모니터링한다.

### 발생한 금융거래

- 거래 유형: 계좌이체
- 거래 특성: 비밀번호 변경과 이체 한도 상향 후 짧은 시간 안에 발생한 고액 송금
- 금액 특성: 고객의 평소 이체 금액보다 크거나 변경 전 한도를 초과해 한도 상향이 필요했던 금액
- 실제 금액 기준과 `짧은 시간`의 범위는 이 문서에서 확정하지 않는다.

### 거래 전후 행동 이벤트

```text
PASSWORD_CHANGED
→ TRANSFER_LIMIT_CHANGED
→ 필요 시 BENEFICIARY_REGISTERED
→ TRANSFER_REQUESTED
```

- 거래 전: 비밀번호 변경, 이체 한도 상향, 선택적으로 신규 수취인 등록
- 거래 후: 추가 인증 결과, 후속 이체 시도와 한도 재변경 여부를 관찰한다.

### 필요한 데이터

- 비밀번호 변경 시각과 변경 결과
- 이체 한도 변경 시각, 변경 전·후 한도와 변경 방향
- 거래 시각, 금액, 출금·수취 계좌
- 수취인 등록 시각과 최초 수취인 여부
- 고객별 평균 거래 금액과 최근 거래 이력
- 로그인 기기·IP·지역과 보안 Mock 신호
- 본인확인 및 추가 인증 Mock 결과
- 현재 외부 위험계좌·위험 기기 결과와 조회 상태. 위험 IP는 향후 후보

### 적용 가능한 Rule

- 거래 직전 비밀번호 변경
- 거래 직전 이체 한도 변경
- 고객 평균 대비 고액 거래
- 최초 수취 계좌
- 신규 기기, 해외 IP 또는 새벽 시간대 거래
- 현재 외부 위험계좌·위험 기기 일치. 위험 IP 일치는 향후 후보

Rule v1에서 이 시나리오와 직접 연결되는 Baseline은 R001, R003과 선택적인 R004이다. R003은 `TRANSFER_LIMIT_CHANGED` 이벤트 존재와 순서를 사용할 뿐 실제 한도 상향·상향 폭을 판단하지 않는다. 정확한 조건과 점수는 [Rule v1 탐지 계약](./rule-v1-detection-contract.md)을 따른다.

### ML이 사용할 수 있는 Feature

- 비밀번호 변경 후 거래까지의 경과 시간
- 이체 한도 변경 후 거래까지의 경과 시간
- 변경 전·후 한도 비율
- 현재 거래 금액과 평균 대비 거래 금액 비율
- 변경된 한도 대비 거래 금액 비율
- 신규 수취 계좌 여부
- 최근 행동 이벤트의 종류, 순서와 개수
- 신규 기기·해외 IP 여부
- 최근 로그인 실패 횟수와 OTP 재발급 여부

### 예상 위험등급

- 비밀번호 변경, 한도 상향과 고액 송금이 짧은 시간에 연속 발생하면 HIGH 후보로 분석한다.
- 신규 기기, 신규 수취인 또는 외부 위험정보 일치가 결합되면 CRITICAL 후보가 될 수 있다.
- 정상적인 변경과 추가 인증이 확인되더라도 최종 등급 조정 방식은 별도 정책으로 결정한다.

### 시스템 자동 대응

- 위험등급별 공통 대응 정책에 따라 Mock 승인, 모니터링, 추가 인증 또는 보류를 적용한다.
- HIGH 이상이면 사건을 생성하고 행동 이벤트의 순서와 각 이벤트 간 경과 시간을 근거로 저장한다.
- CRITICAL이면 담당자에게 긴급 알림을 제공한다.

### 사건 생성 조건

- 최종 위험등급이 HIGH 또는 CRITICAL인 경우
- 비밀번호 변경과 한도 상향 후 고액 송금 시퀀스가 승인된 사건 생성 정책을 충족한 경우
- 동일 세션의 반복 이체는 하나의 사건에 연관 거래로 묶을 수 있다.

### 담당자 확인 항목

- 고객이 비밀번호와 한도 변경을 직접 수행했는지
- 변경 과정의 Mock 본인확인 결과와 추가 인증 결과
- 기기·IP·지역이 평소 패턴과 일치하는지
- 한도 상향과 고액 송금의 정상적인 목적이 확인되는지
- 수취인이 기존 거래 관계인지
- OTP 재발급, 로그인 실패 또는 원격제어 앱 신호가 동반되었는지
- 동일 수취 계좌와 연결된 다른 의심 거래가 있는지

### 최종 처리 예시

- 고객이 모든 변경과 송금을 인정하고 정상 목적과 인증 결과가 확인되면 `NORMAL` 또는 `FALSE_POSITIVE`로 처리한다.
- 고객이 변경이나 송금을 부인하고 신규 기기·위험 수취인 등 복합 신호가 확인되면 `CONFIRMED_FRAUD`로 처리하고 Mock 후속 조치를 기록한다.

### 아직 추가 결정이 필요한 사항

- Rule v1의 24시간 실험값 검증과 후속 위험 관찰 시간
- 실제 한도 상향·상향 폭을 판단할 추가 입력과 후속 Rule
- 비밀번호 변경과 한도 변경 중 일부 이벤트만 발생한 경우의 Rule 조합
- 정상 본인확인 결과가 위험등급에 미치는 영향
- 동일 세션·동일 사건으로 묶을 거래 범위

## 5. FDS-SCN-003 외부 위험계좌로 송금

### 목적

수취 계좌가 외부 위험정보 Mock 서비스의 의심 계좌와 일치하는 송금을 탐지하고, 외부 조회 결과와 내부 거래 근거를 함께 관리한다.

이 절은 거래 접수–External Risk–Rule 분석–위험 대응의 최종 목표 시나리오다.
현재는 수신 계좌 match를 재현하는 독립 Mock 경계까지만 구현되었다. 승인된 목표
v2는 이 결과를 분석 Snapshot에 포함하지만 R001~R004·점수·등급·Evidence에는
반영하지 않는다. 외부 위험정보를 점수·거래 대응에 사용하는 것은 별도 정책이다.

### 주요 행위자

- 송금을 요청하는 고객
- 외부 위험정보를 조회하고 대응하는 FDS 시스템
- 위험계좌 정보를 제공하는 외부 위험정보 Mock 서비스
- 사건을 검토하는 FDS 담당자

### 사전 조건

- 송금 전에 수취 계좌를 식별할 수 있다.
- 외부 위험정보 Mock 서비스가 계좌의 위험 여부, 근거, 기준 시각과 조회 상태를 반환할 수 있다.
- 조회 timeout·unavailable·invalid response를 typed failure로 분류할 수 있다.
  retry·cache·Circuit Breaker·fallback은 현재 적용하지 않는다.

### 분석 트리거

- 실시간 거래 요청: 송금 요청 시 수취 계좌의 외부 위험정보와 내부 거래 근거를 분석한다.
- 외부 위험정보 갱신: 수취 계좌의 위험정보가 신규 등록·변경되면 관련 거래와 열린 사건을 재검토한다.
- 연관 거래 추가: 같은 수취 계좌와 연결된 거래가 추가되면 계좌 관계와 사건 근거를 갱신한다.
### 정상 비교 흐름

1. 고객이 계좌이체를 요청한다.
2. 시스템이 수취 계좌의 외부 위험정보를 조회한다.
3. FastAPI v2가 일치·불일치 Snapshot을 검증하지만 현재 R001~R004는 이를 사용하지
   않고 기존 Rule 결과를 산출한다.
4. 최종 위험등급에 따라 Mock 거래 대응을 수행한다.

### 발생한 금융거래

- 거래 유형: 내부 또는 타행 계좌이체
- 거래 특성: 수취 계좌가 외부 의심 계좌 정보와 일치
- 금액, 거래 빈도, 최초 수취 여부와 관계없이 외부 일치 정보 자체를 주요 탐지 근거로 사용하되 단독 최종 판정으로 사용하지 않는다.

### 거래 전후 행동 이벤트

```text
필요 시 BENEFICIARY_REGISTERED
→ TRANSFER_REQUESTED
→ 외부 위험정보 조회
→ Mock 거래 대응
```

- 거래 전: 수취인 등록, 로그인·기기·IP 신호
- 거래 후: 같은 수취 계좌로의 재시도, 다른 계좌를 이용한 우회 송금을 관찰한다.

### 필요한 데이터

- 거래 식별 정보, 시각, 금액, 출금·수취 계좌
- 최초 수취인 여부와 과거 거래 관계
- 외부 위험정보 일치 여부, 위험 유형, 제공 시각과 유효 기준
- 외부 조회 성공 상태·Provider 기준 시각 또는 typed failure category. cache와
  stale data는 현재 사용하지 않음
- 고객의 거래 패턴, 기기와 IP 정보
- 동일 수취 계좌로 유입된 다른 고객의 거래 집계

### 적용 가능한 Rule

- 외부 위험계좌 일치 Rule은 향후 별도 Rule·scoring 승인 후보
- 최초 수취 계좌
- 고객 평균 대비 고액 거래
- 신규 기기 또는 해외 IP 거래
- 짧은 시간 내 동일·다른 계좌로 반복 송금
- 여러 고객의 자금이 동일 수취 계좌로 집중

### ML이 사용할 수 있는 Feature

- 외부 위험계좌 일치 여부와 위험정보의 최신성
- 현재 거래 금액과 평균 대비 비율
- 수취 계좌의 최근 입금 고객 수와 입금 횟수
- 고객과 수취 계좌의 최초 거래 여부
- 최근 10분 거래 횟수와 최근 24시간 거래 금액
- 신규 기기·해외 IP 여부
- 외부 위험정보 성공 여부와 typed failure category. cache 사용은 향후 별도 후보

### 예상 위험등급

- 현재 R001~R004의 위험등급은 External Risk와 무관하게 기존 점수 계약으로
  계산한다.
- 외부 위험계좌 일치의 등급 가산, 단독 대응과 결합 조건은 별도 Rule·scoring
  정책에서 확정한다.

### 시스템 자동 대응

- 최종 위험등급이 HIGH이면 Mock 추가 인증을 요구하고 사건을 생성한다.
- CRITICAL이면 Mock 거래 보류, 긴급 사건 생성과 담당자 알림을 수행한다.
- 현재 구현된 FastAPI v2는 External Risk를 인메모리 요청에만 포함하고 Evidence·AuditLog·DB에
  저장하지 않는다. 향후 감사·영속 요구는 별도 승인이 필요하다.

### 사건 생성 조건

- 외부 위험계좌 일치 결과를 포함한 최종 위험등급이 HIGH 또는 CRITICAL인 경우
- 같은 위험 수취 계좌와 관련된 거래는 계좌와 자금 흐름을 기준으로 하나의 사건에 연결할 수 있다.
- 재시도된 동일 거래가 중복 사건을 만들지 않도록 사건 생성의 멱등성을 보장해야 한다.

### 담당자 확인 항목

- 외부 위험정보의 유형, 제공 시각과 최신성
- 완전 일치인지 식별 정보 정규화에 따른 일치인지
- 고객과 수취인의 정상 거래 관계
- 동일 수취 계좌로 유입된 다른 고객 거래와 관련 사건
- 고객의 기기·IP·행동 이벤트와 거래 금액 패턴
- 조회 결과의 Provider 기준 시각과 match 근거. cache는 현재 미구현
- 고객 추가 인증과 거래 확인 결과

### 최종 처리 예시

- 위험정보가 최신이고 고객이 송금을 부인하며 연관 의심 거래가 확인되면 `CONFIRMED_FRAUD`로 처리한다.
- 외부 위험정보가 정정되었거나 동명이 아닌 식별 오류 등으로 일치가 무효이고 정상 거래 관계가 확인되면 `FALSE_POSITIVE` 또는 `NORMAL`로 처리한다.

### 외부 위험정보 서비스 장애 처리

- 공통 fail-closed 장애 처리 정책을 적용해 Rule 분석을 시작하지 않는다.
- 자동 재조회나 fallback은 없다. 서비스 복구 후 재조회·근거 정정은 향후 별도
  승인된 실행 경로에서 감사 이력과 함께 다룬다.
### 아직 추가 결정이 필요한 사항

- 위험계좌 정보의 식별·정규화와 일치 기준
- 위험정보 유형, 최신성, 유효기간과 위험도 반영 정책
- 외부 정보 단독 일치 시 Mock 거래 대응 수준
- cache·Circuit Breaker·fallback 도입 여부와 복구 후 재조회 정책. 별도
  Issue·ADR 승인 필요
- 외부 정보 정정 시 사건과 거래 근거의 변경 처리 방식

## 6. FDS-SCN-004 짧은 시간 동안 여러 계좌로 분산 송금

### 목적

한 고객 또는 한 출금 계좌에서 짧은 시간 동안 여러 수취 계좌로 자금을 나누어 보내는 분산 송금 패턴을 탐지한다.

### 주요 행위자

- 여러 송금을 요청하는 고객
- 거래 집계와 시퀀스를 분석하는 FDS 시스템
- 사건을 검토하는 FDS 담당자
- 외부 위험정보 Mock 서비스

### 사전 조건

- 동일 고객과 출금 계좌의 거래를 시간 창으로 집계할 수 있다.
- 수취 계좌 수, 거래 횟수와 총 송금액을 계산할 수 있다.
- 기준 문서의 대표 관찰 구간인 최근 10분 거래를 조회할 수 있다.

### 분석 트리거

- 실시간 거래 요청: 각 송금 요청을 개별 분석하고 시간 창 집계에 반영한다.
- 시간 창 집계 갱신: 동일 고객·출금 계좌의 거래 횟수, 고유 수취 계좌 수와 누적 금액이 갱신될 때 집계형 분석을 수행한다.
- 연관 거래 추가: 관찰 중인 시간 창에 새 거래가 추가되면 거래 묶음의 위험도와 사건 연결 여부를 다시 평가한다.
- 외부 위험정보 갱신: 수취 계좌의 위험정보가 갱신되면 거래 묶음의 근거를 보완한다.
### 정상 비교 흐름

1. 고객이 정상 목적에 따라 하나 이상의 계좌로 송금한다.
2. 거래 빈도, 수취 계좌 수와 총액이 승인된 정상 범위 안에 있다.
3. 시스템은 개별 거래와 시간 창 집계를 분석하고 위험등급에 따라 처리한다.

### 발생한 금융거래

- 거래 유형: 반복 계좌이체
- 거래 특성: 기준 문서의 대표 흐름인 10분 동안 여러 계좌로 반복 송금
- 분석 단위: 개별 거래와 동일 고객·출금 계좌의 시간 창 내 거래 묶음
- 거래 건수, 수취 계좌 수, 총액과 개별 금액 기준은 이 문서에서 확정하지 않는다.

### 거래 전후 행동 이벤트

```text
반복적인 BENEFICIARY_REGISTERED
→ 반복적인 TRANSFER_REQUESTED
→ 추가 송금 시도 또는 종료
```

- 거래 전: 여러 신규 수취인 등록, 로그인·기기 변화
- 거래 중: 짧은 간격의 반복 이체 요청
- 거래 후: 한도 변경, 다른 채널을 통한 후속 거래와 재시도를 관찰한다.

### 필요한 데이터

- 고객·출금 계좌·수취 계좌 식별 정보
- 각 거래의 시각, 금액, 상태와 채널
- 최근 10분 거래 횟수, 고유 수취 계좌 수와 누적 금액
- 최근 24시간 거래 횟수·금액과 고객의 평소 빈도
- 각 수취 계좌의 최초 거래 여부
- 행동 이벤트, 기기, IP와 세션 정보
- 수취 계좌별 외부 위험정보와 조회 상태

### 적용 가능한 Rule

- 최근 10분 내 반복 이체
- 짧은 시간 내 여러 수취 계좌로 송금
- 다수의 최초 수취 계좌
- 최근 24시간 누적 거래 금액 급증
- 고객 평균 대비 개별 또는 누적 고액 거래
- 신규 기기, 해외 IP 또는 새벽 시간대 거래
- 외부 위험계좌 일치

### ML이 사용할 수 있는 Feature

- 최근 10분 거래 횟수와 고유 수취 계좌 수
- 최근 10분·24시간 누적 송금액
- 거래 간 평균·최소 시간 간격
- 개별 금액의 분포와 고객 평소 패턴 대비 변화
- 신규 수취 계좌 비율
- 잔액 대비 누적 출금 비율
- 신규 기기·해외 IP 여부
- 외부 위험계좌와 일치한 수취 계좌 수

### 예상 위험등급

- 반복 횟수 또는 수취 계좌 수가 비정상적이면 MEDIUM 이상 후보로 분석한다.
- 누적 고액, 다수 신규 수취인 또는 외부 위험계좌가 결합되면 HIGH·CRITICAL 후보가 될 수 있다.

### 시스템 자동 대응

- 시간 창이 갱신될 때 거래 묶음의 위험도를 다시 분석한다.
- MEDIUM이면 Mock 승인 후 모니터링 대상으로 등록할 수 있다.
- HIGH이면 Mock 추가 인증과 사건 생성을 수행한다.
- CRITICAL이면 후속 거래에 Mock 보류를 적용하고 긴급 사건과 담당자 알림을 생성한다.

### 사건 생성 조건

- 시간 창 내 거래 묶음의 최종 위험등급이 HIGH 또는 CRITICAL인 경우
- 동일 고객·출금 계좌의 연속 거래를 하나의 사건에 연결한다.
- 시간 창이 겹치거나 집계가 재실행되어도 동일 거래로 중복 사건을 생성하지 않는다.

### 담당자 확인 항목

- 각 수취 계좌와 고객의 관계 및 정상적인 분산 송금 목적
- 거래 간격, 총 거래 횟수, 고유 수취 계좌 수와 누적 금액
- 신규 수취인 비율과 등록 시점
- 거래 실패 후 금액·수취인을 바꾼 재시도 여부
- 기기·IP·지역과 로그인 행동의 변화
- 수취 계좌의 외부 위험정보와 다른 사건 연계
- 고객 확인과 Mock 추가 인증 결과

### 최종 처리 예시

- 가족 송금이나 정기 정산 등 정상 목적과 수취 관계가 확인되면 `NORMAL` 또는 `FALSE_POSITIVE`로 처리한다.
- 고객이 거래를 부인하거나 다수 위험 수취인으로의 분산이 확인되면 `CONFIRMED_FRAUD`로 처리하고 관련 거래를 하나의 사건에 유지한다.

### 외부 위험정보 서비스 장애 처리

- 공통 fail-closed 장애 처리 정책을 적용한다.
- 복수 수취 계좌 중 하나라도 필수 조회가 실패하면 실패를 `UNMATCHED`로 바꾸거나
  cache로 대체하지 않고 Rule 분석을 시작하지 않는다. 부분 성공 처리와 재분석은
  향후 별도 계약 대상이다.
### 아직 추가 결정이 필요한 사항

- 시간 창의 고정·이동 방식과 관찰 기간
- 거래 횟수, 고유 수취 계좌 수와 누적 금액 기준
- 실패·취소·보류 거래를 집계에 포함하는 방식
- 겹치는 시간 창과 사건 병합 기준
- 정상적인 다건 송금 고객의 예외 또는 기준선 처리

## 7. FDS-SCN-005 여러 고객의 자금이 특정 계좌로 집중

### 목적

서로 다른 여러 고객의 자금이 짧은 기간에 동일한 수취 계좌로 집중되는 집금 또는 대포통장 의심 패턴을 탐지한다.

### 주요 행위자

- 송금하는 여러 고객
- 자금이 집중되는 수취 계좌의 명의 고객
- 계좌 관계와 자금 흐름을 분석하는 FDS 시스템
- 사건을 검토하는 FDS 담당자
- 외부 위험정보 Mock 서비스

### 사전 조건

- 수취 계좌를 기준으로 여러 송금 고객과 거래를 집계할 수 있다.
- 최근 24시간 입금자 수, 입금 횟수와 총액을 계산할 수 있다.
- 하나의 사건에 여러 고객·계좌·거래를 연결할 수 있다는 업무 요구사항이 정의되어 있다.

### 분석 트리거

- 시간 창 집계 갱신: 수취 계좌별 고유 입금 고객 수, 거래 수와 누적 금액이 갱신될 때 계좌 중심 집계 분석을 수행한다.
- 연관 거래 추가: 동일 수취 계좌로 새 입금이나 후속 출금 거래가 추가되면 자금 흐름과 사건 연결 여부를 다시 평가한다.
- 외부 위험정보 갱신: 집중 계좌의 위험정보가 갱신되면 열린 사건과 관련 거래의 근거를 보완한다.
### 정상 비교 흐름

1. 수취 계좌가 통상적인 고객 간 송금을 수신한다.
2. 입금 고객 수, 거래 빈도와 총액이 해당 계좌의 평소 패턴에서 크게 벗어나지 않는다.
3. 시스템이 수취 계좌 중심의 집계를 수행하고 위험 신호가 없으면 별도 사건을 생성하지 않는다.

### 발생한 금융거래

- 거래 유형: 여러 계좌에서 하나의 계좌로 향하는 계좌이체
- 거래 특성: 서로 다른 여러 고객의 출금 계좌에서 동일 수취 계좌로 자금이 집중
- 분석 단위: 수취 계좌를 중심으로 연결한 복수 거래
- 집중 판단 기간, 고객 수, 거래 수와 총액 기준은 이 문서에서 확정하지 않는다.

### 거래 전후 행동 이벤트

```text
여러 고객의 TRANSFER_REQUESTED
→ 동일 계좌로 반복 입금
→ 수취 계좌의 후속 이체 또는 ATM 인출 가능
```

- 송금 고객별 로그인·기기·수취인 등록 이벤트를 확인한다.
- 수취 계좌의 입금 직후 재송금·ATM 인출 여부는 후속 위험 흐름으로 연결해 관찰하되 별도 분석 대상을 추가하지 않는다.

### 필요한 데이터

- 출금 고객·출금 계좌·수취 계좌 식별 정보
- 거래 시각, 금액, 상태와 채널
- 수취 계좌의 최근 24시간 고유 입금 고객 수, 거래 수와 총 입금액
- 수취 계좌의 과거 입금 패턴과 계좌 사용 기간
- 입금 후 출금까지의 경과 시간과 즉시 출금 비율
- 관련 기기·IP와 하나의 기기에서 접근한 계좌 수
- 수취 계좌의 외부 위험정보와 조회 상태

### 적용 가능한 Rule

- 여러 고객이 동일 수취 계좌로 반복 송금
- 수취 계좌의 최근 입금자 수 또는 입금 횟수 급증
- 수취 계좌의 최근 24시간 입금액 급증
- 외부 위험계좌 일치
- 입금 후 단시간 내 재송금 또는 ATM 인출
- 하나의 기기에서 여러 계좌 접근

### ML이 사용할 수 있는 Feature

- 최근 24시간 고유 입금 고객 수와 입금 횟수
- 최근 24시간 총 입금액과 평소 대비 증가율
- 입금 금액 분포와 거래 간격
- 최초 송금 고객 비율
- 입금 후 출금까지의 경과 시간
- 입금액 대비 즉시 출금 비율
- 하나의 기기·IP와 연결된 계좌 수
- 외부 위험계좌 여부

### 예상 위험등급

- 입금 고객 수나 빈도의 비정상적 증가만 확인되면 MEDIUM 이상 후보로 분석한다.
- 외부 위험계좌 일치, 즉시 자금 이동 또는 다계좌 접근이 결합되면 HIGH·CRITICAL 후보가 될 수 있다.

### 시스템 자동 대응

- 수취 계좌 중심으로 관련 거래를 연결하고 위험도를 갱신한다.
- HIGH이면 사건을 생성하고 필요 시 이후 거래에 Mock 추가 인증을 요구한다.
- CRITICAL이면 후속 거래에 Mock 보류를 적용하고 긴급 사건과 담당자 알림을 생성한다.
- 이미 열린 사건이 있으면 정책에 따라 새 거래를 기존 사건에 연결한다.

### 사건 생성 조건

- 수취 계좌 중심 집계 결과가 HIGH 또는 CRITICAL인 경우
- 여러 고객의 관련 거래를 하나의 대표 사건에 연결할 수 있다.
- 기존 사건 연결과 신규 사건 생성의 우선순위는 별도 병합 정책을 따른다.

### 담당자 확인 항목

- 수취 계좌의 개설·사용 기간과 평소 입금 패턴
- 입금 고객 간 관계와 정상적인 집금 목적
- 최근 입금 고객 수, 거래 수, 총액과 시간 분포
- 입금 후 재송금·ATM 인출의 속도와 비율
- 동일 기기·IP에서 여러 계좌에 접근했는지
- 외부 위험계좌 정보와 기존 사건 연계
- 관련 고객의 거래 확인 결과

### 최종 처리 예시

- 모임 회비나 공동 정산처럼 정상 집금 목적과 고객 관계가 확인되면 `NORMAL` 또는 `FALSE_POSITIVE`로 처리한다.
- 다수 고객이 송금을 부인하고 수취 직후 자금이 이동했으며 위험계좌 연계가 확인되면 `CONFIRMED_FRAUD`로 처리한다.

### 아직 추가 결정이 필요한 사항

- 집중 거래 판단 기간과 최소 고객·거래 수

- 후속 거래에 적용할 Mock 대응 범위

## 8. FDS-SCN-006 고액 입금 후 단시간 내 ATM 인출

### 목적

고액 자금을 수신한 계좌에서 짧은 시간 안에 잔액 대부분을 ATM으로 인출하는 현금화 의심 흐름을 탐지한다.

### 주요 행위자

- 입금받은 뒤 ATM 인출을 요청하는 고객
- 입금 거래와 ATM 인출을 연결해 분석하는 FDS 시스템
- 사건을 검토하는 FDS 담당자
- 외부 위험정보 Mock 서비스

### 사전 조건

- 계좌의 입금 거래와 이후 ATM 인출을 시간 순서로 연결할 수 있다.
- 입금 후 출금까지의 경과 시간과 입금액 대비 인출 비율을 계산할 수 있다.
- ATM 위치, 이용 시각과 Mock 인출 상태를 확인할 수 있다.

### 분석 트리거

- 실시간 거래 요청: ATM 인출 요청 시 선행 입금, 경과 시간과 인출 비율을 분석한다.
- 연관 거래 추가: 고액 입금 또는 반복 ATM 인출이 추가되면 연결된 자금 흐름의 위험도를 갱신한다.
- 시간 창 집계 갱신: 최근 ATM 인출 횟수와 고유 ATM 수가 갱신될 때 반복 인출 패턴을 재평가한다.
### 정상 비교 흐름

1. 고객 계좌에 정상적인 자금이 입금된다.
2. 고객이 평소 이용 지역과 시간대에서 통상적인 금액을 인출한다.
3. 입금과 인출 사이의 시간, 금액 비율과 고객 패턴을 분석한 결과 위험 신호가 없으면 거래를 승인한다.

### 발생한 금융거래

- 선행 거래: 고객 계좌로의 고액 입금 또는 송금 수신
- 후행 거래: 단시간 내 ATM 현금 인출
- 금액 특성: 입금된 금액 또는 계좌 잔액의 대부분을 인출
- `고액`, `단시간`과 `대부분`의 수치 기준은 이 문서에서 확정하지 않는다.

### 거래 전후 행동 이벤트

```text
고액 입금 수신
→ ATM_WITHDRAWAL_REQUESTED
→ 필요 시 반복 ATM_WITHDRAWAL_REQUESTED
```

- 거래 전: 입금 발생, 로그인·잔액 확인 등 사용 가능한 행동 이벤트
- 거래 시점: ATM 인출 요청
- 거래 후: 다른 ATM에서의 반복 인출, 잔여 자금의 이체를 관찰한다.

### 필요한 데이터

- 선행 입금과 ATM 인출의 거래 식별 정보, 시각과 금액
- 입금 송신 계좌와 수신 계좌
- 입금 후 인출까지의 경과 시간
- 입금액 대비 인출액 비율과 인출 직전·후 잔액
- ATM 식별 정보, 위치와 이용 시각
- 최근 ATM 이용 지역, 시간대, 횟수와 금액 패턴
- 최근 여러 ATM 사용 여부
- 송신·수신 계좌의 외부 위험정보와 조회 상태

### 적용 가능한 Rule

- 고액 입금 직후 ATM 인출
- 입금액 또는 잔액 대부분 인출
- 새벽 시간대 ATM 인출
- 평소와 다른 지역의 ATM 사용
- 짧은 시간 여러 ATM에서 반복 인출
- 외부 위험계좌에서 입금

### ML이 사용할 수 있는 Feature

- 입금 후 ATM 인출까지의 경과 시간
- 입금액 대비 인출액 비율
- 잔액 대비 인출액 비율
- 현재 인출 금액과 고객 평균 대비 비율
- 최근 시간 창의 ATM 인출 횟수와 고유 ATM 수
- 평소 이용 지역과 현재 ATM 간 차이
- 거래 시간대
- 선행 입금 송신 계좌의 외부 위험 여부

### 예상 위험등급

- 고액 입금 직후 대부분을 인출하면 HIGH 후보로 분석한다.
- 위험계좌에서의 입금, 여러 ATM 반복 이용 또는 비정상 지역·시간대가 결합되면 CRITICAL 후보가 될 수 있다.

### 시스템 자동 대응

- 위험등급에 따라 ATM 인출에 Mock 승인, 추가 인증 또는 보류 상태를 적용한다.
- HIGH 이상이면 선행 입금과 ATM 인출을 연결한 사건을 생성한다.
- CRITICAL이면 긴급 사건 생성과 담당자 알림을 수행한다.
- 실제 ATM 거래 차단이나 실제 현금 인출 제어는 수행하지 않는다.

### 사건 생성 조건

- 연결된 입금·인출 흐름의 최종 위험등급이 HIGH 또는 CRITICAL인 경우
- 반복 ATM 인출은 기존 사건에 연관 거래로 추가할 수 있다.
- 선행 입금과 후행 인출의 연결 근거와 계산 기준 시각을 사건에 남긴다.

### 담당자 확인 항목

- 선행 입금의 송신 계좌, 금액과 정상적인 자금 출처
- 입금 후 인출까지의 경과 시간과 인출 비율
- ATM 위치·시간대가 고객의 평소 패턴과 일치하는지
- 여러 ATM을 이동하며 반복 인출했는지
- 고객이 입금과 인출을 모두 인정하는지
- 송신 계좌의 외부 위험정보와 관련 사건
- Mock 추가 인증 결과

### 최종 처리 예시

- 고객이 정상적인 자금 수령과 현금 사용 목적을 확인하고 평소 이용 패턴과 부합하면 `NORMAL` 또는 `FALSE_POSITIVE`로 처리한다.
- 고객이 거래를 부인하거나 위험계좌에서 받은 자금을 여러 ATM에서 즉시 현금화한 흐름이 확인되면 `CONFIRMED_FRAUD`로 처리한다.

### 아직 추가 결정이 필요한 사항

- 고액 입금, 단시간과 대부분 인출의 기준
- 여러 입금 중 어떤 거래를 선행 자금으로 연결할지에 대한 기준
- ATM 거리·지역 이상 여부의 판단 방식
- 반복 ATM 인출을 동일 사건으로 묶는 시간 범위

## 9. FDS-SCN-007 대출 실행 거래 후 자금 이동

### 목적

### 주요 행위자

- 대출금이 입금된 뒤 송금을 요청하는 고객

- 사건을 검토하는 FDS 담당자
- 외부 위험정보 Mock 서비스

### 사전 조건

- 실제 대출 상품·심사·실행 기능은 구현하지 않고 `LOAN_DISBURSED` Mock 금융거래를 입력받는다.
- 대출 실행 금액과 후속 송금 거래를 같은 고객·계좌 기준으로 연결할 수 있다.

2. 고객이 기존 수취인에게 정상적인 목적의 자금을 이체하거나 자금을 계좌에 유지한다.
3. 시스템은 대출금 대비 이동 금액과 행동 흐름을 분석하고 정책에 따라 처리한다.

### 거래·행동 흐름

```text
LOAN_DISBURSED Mock 금융거래
→ BENEFICIARY_REGISTERED 행동 이벤트

```

- 거래 전: Mock 대출 실행, 신규 수취인 등록
- 거래 후: 추가 송금, 수취 계좌의 재송금 또는 ATM 인출을 관찰한다.

### 필요한 데이터

- 대출금 대부분으로 판단할 비율
- 여러 후속 송금과 대출 실행 이벤트를 연결하는 기준
- Mock 대출 이벤트의 필수 데이터와 중복 식별 방식
- 정상적인 대출금 사용을 구분할 검토 기준

## 10. FDS-SCN-008 여러 오픈뱅킹 계좌의 자금 집중 및 재송금

### 목적

여러 외부 금융기관 계좌를 등록하고 각 계좌의 자금을 하나의 계좌로 집중한 뒤 다른 계좌로 즉시 재송금하는 자금 세탁 또는 계정 탈취 의심 흐름을 탐지한다.

### 주요 행위자

- 여러 오픈뱅킹 계좌를 등록하고 자금을 이동하는 고객
- 오픈뱅킹 거래와 계좌 관계를 분석하는 FDS 시스템
- 외부 금융기관을 모사하는 Mock 서비스
- 사건을 검토하는 FDS 담당자
- 외부 위험정보 Mock 서비스

### 사전 조건

- 외부 금융기관 계좌 등록과 출금은 Mock 연동으로 처리한다.
- 고객의 여러 외부 계좌, 집중 계좌와 최종 수취 계좌를 하나의 자금 흐름으로 연결할 수 있다.
- 각 단계의 거래 시각, 금액과 상태를 확인할 수 있다.

### 분석 트리거

- 행동 이벤트 발생: 여러 외부 계좌 등록이 확인되면 후속 오픈뱅킹 거래 관찰을 시작한다.
- 실시간 거래 요청: 오픈뱅킹 출금 또는 후속 재송금 요청 시 연결된 자금 흐름을 분석한다.
- 시간 창 집계 갱신: 외부 계좌 수, 집중 거래 수와 누적 금액이 갱신될 때 집계형 분석을 수행한다.
- 연관 거래 추가: 집중 계좌의 입금·재송금이 추가되면 사건 연결 여부와 위험도를 다시 평가한다.
### 정상 비교 흐름

1. 고객이 본인 소유의 외부 계좌를 Mock 오픈뱅킹으로 등록한다.
2. 고객이 정상적인 자금 관리 목적으로 자금을 한 계좌에 모은다.
3. 즉시 재송금하지 않거나 기존 수취인에게 평소 패턴의 금액을 송금한다.
4. 시스템은 계좌 수, 집중 금액, 경과 시간과 수취 관계를 분석한다.

### 발생한 금융거래

- 거래 유형: 오픈뱅킹 출금 및 계좌이체
- 거래 흐름: 여러 외부 계좌 등록 → 각 외부 계좌에서 출금 → 하나의 계좌로 집중 → 다른 계좌로 즉시 재송금
- 분석 단위: 여러 외부 계좌에서 최종 수취 계좌까지 연결된 복수 거래
- 계좌 수, 집중 비율과 즉시 재송금 시간 기준은 이 문서에서 확정하지 않는다.

### 거래 전후 행동 이벤트

```text
여러 외부 계좌 등록
→ 반복적인 OPEN_BANKING_TRANSFER
→ 하나의 계좌로 자금 집중
→ 필요 시 BENEFICIARY_REGISTERED
→ TRANSFER_REQUESTED
```

- 거래 전: 여러 외부 계좌 등록, 로그인·기기·보안 이벤트
- 거래 중: 각 계좌 출금과 집중 계좌 입금
- 거래 후: 다른 계좌로 즉시 재송금, 추가 분산 또는 ATM 인출을 관찰한다.

### 필요한 데이터

- 고객과 내부·외부 계좌의 식별 정보 및 소유 관계 Mock 결과
- 외부 계좌 등록 시각과 등록 계좌 수
- 각 오픈뱅킹 출금의 시각, 금액, 상태와 Mock 금융기관
- 집중 계좌의 입금 거래와 누적 금액
- 집중 후 재송금까지의 경과 시간과 금액 비율
- 최종 수취 계좌의 최초 거래 여부
- 고객의 기기·IP·행동 이벤트와 과거 오픈뱅킹 패턴
- 관련 계좌의 외부 위험정보와 조회 상태

### 적용 가능한 Rule

- 짧은 시간 내 여러 외부 계좌 등록
- 여러 외부 계좌에서 하나의 계좌로 자금 집중
- 오픈뱅킹 출금 후 즉시 재송금
- 집중 금액 대부분을 다른 계좌로 송금
- 최초 수취 계좌
- 신규 기기, 해외 IP 또는 보안 위험 신호
- 외부 위험계좌 일치

### ML이 사용할 수 있는 Feature

- 최근 등록한 외부 계좌 수
- 자금을 출금한 고유 외부 계좌 수
- 집중 거래 횟수와 누적 금액
- 첫 출금부터 집중 완료까지의 시간
- 집중 완료 후 재송금까지의 시간
- 집중 금액 대비 재송금 비율
- 고객의 평소 오픈뱅킹 계좌 수·금액 대비 변화
- 신규 수취 계좌, 신규 기기와 해외 IP 여부
- 관련 계좌 중 외부 위험계좌 수

### 예상 위험등급

- 여러 외부 계좌의 자금 집중과 즉시 재송금이 결합되면 HIGH 후보로 분석한다.
- 신규 기기·신규 수취인, 위험계좌 또는 비정상 보안 신호가 함께 확인되면 CRITICAL 후보가 될 수 있다.

### 시스템 자동 대응

- Mock 오픈뱅킹 거래와 후속 송금을 하나의 자금 흐름으로 연결해 위험도를 갱신한다.
- HIGH이면 Mock 추가 인증과 사건 생성을 수행한다.
- CRITICAL이면 후속 재송금에 Mock 보류를 적용하고 긴급 사건과 담당자 알림을 생성한다.
- 외부 금융기관의 실제 계좌 등록 취소, 출금 중지나 자금 차단은 수행하지 않는다.

### 사건 생성 조건

- 연결된 오픈뱅킹 자금 흐름의 최종 위험등급이 HIGH 또는 CRITICAL인 경우
- 여러 외부 계좌의 출금과 최종 재송금을 하나의 사건에 연결한다.
- Mock 외부기관 응답 재처리와 중복 이벤트로 동일 거래·사건이 중복 생성되지 않아야 한다.

### 담당자 확인 항목

- 등록한 외부 계좌가 고객 본인 소유인지에 대한 Mock 확인 결과
- 외부 계좌 등록 수와 등록·출금 간격
- 각 계좌의 출금액, 집중 총액과 재송금 비율
- 집중 완료 후 재송금까지의 경과 시간
- 최종 수취 계좌와 고객의 거래 관계
- 신규 기기·IP·보안 이벤트와 고객 확인 결과
- 관련 계좌의 외부 위험정보와 기존 사건 연계
- Mock 외부기관의 지연·실패·중복 응답 여부

### 최종 처리 예시

- 고객이 본인 계좌 간 정상적인 자금 통합과 최종 송금 목적을 확인하고 소유 관계가 일치하면 `NORMAL` 또는 `FALSE_POSITIVE`로 처리한다.
- 고객이 외부 계좌 등록이나 재송금을 부인하거나 위험계좌로 자금이 즉시 이동한 경우 `CONFIRMED_FRAUD`로 처리한다.

### 외부 위험정보 서비스 장애 처리

- 외부 금융기관 Mock 연동 장애와 외부 위험정보 서비스 장애를 구분해 기록한다.
- 외부 위험정보 장애에는 공통 장애 처리 정책을 적용한다.
- 외부 금융기관 Mock 응답이 불명확하면 거래 결과를 임의로 성공 처리하지 않고 해당 Mock 연동 상태를 기록한다.
### 아직 추가 결정이 필요한 사항

- 자금 집중으로 판단할 외부 계좌 수, 관찰 시간과 집중 비율
- 즉시 재송금의 시간과 금액 비율 기준
- 외부 계좌 소유 관계 Mock 검증의 처리 정책
- 여러 Mock 외부기관의 부분 성공·실패와 보상 처리 방식
- 자금 흐름 사건의 병합·분리와 종료 기준
