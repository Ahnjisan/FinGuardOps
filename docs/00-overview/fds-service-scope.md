# FinGuardOps 서비스 범위

> Cloud Native 금융 AI 이상거래 탐지·사건 처리·운영 플랫폼

## 프로젝트 구분

- 저장소명: `AI-FINANCIAL-FDS-PLATFORM`
- 제품명: `FinGuardOps`

FinGuardOps는 기존 금융 이상거래 탐지 프로젝트의 금융거래·사용자 행동 분석 범위를 유지하면서 사건 처리, AI 운영, Cloud Native 운영 관점을 강화한 제품이다. 기존 프로젝트를 폐기하고 별도로 시작하는 프로젝트가 아니다.

금융거래와 사용자 행동을 기반으로 이상거래를 탐지하고, 위험 대응과 사건 처리를 지원하며, AI 서비스의 장애·성능·비용을 통합 관리하는 Cloud Native 금융 AI FraudOps 플랫폼을 지향한다.

## 해결하려는 문제

- 탐지 결과를 FDS 분석 담당자가 어떻게 검토하고 설명할 것인가
- 위험 거래와 사건 상태를 어떻게 일관성 있게 관리할 것인가
- 중복 요청·이벤트·사건 생성을 어떻게 방지할 것인가
- AI 및 외부 서비스 장애를 핵심 거래 처리 흐름에서 어떻게 격리할 것인가
- LLM 호출량·입력 토큰·출력 토큰·비용을 어떻게 측정하고 통제할 것인가
- 거래 접수부터 탐지·사건·AI 리포트까지의 흐름을 어떻게 추적할 것인가
- 배포 버전과 서비스 운영 상태를 어떻게 확인할 것인가

## 주요 사용자

### FDS 분석 담당자

- 위험 거래와 사건 조회
- Rule·ML 탐지 근거 검토
- 위험 점수와 위험 등급 확인
- 고객 행동 타임라인 확인
- 연관 거래와 외부 위험정보 확인
- AI 사건 리포트 검토
- 조사 메모 작성
- 사건 상태 변경
- 정상·오탐·이상거래 최종 판정
- 감사 이력 조회

### 플랫폼·클라우드 운영자

- Spring Boot·FastAPI 서비스 상태
- PostgreSQL·Redis 상태와 향후 도입할 Kafka 상태
- API 응답시간·오류율·처리량
- Rule 실행시간과 ML 추론시간
- DB Connection Pool
- Kafka 도입 이후 Consumer Lag
- LLM 호출량
- 입력·출력 토큰
- 모델별 비용
- 캐시 적중률
- fallback 비율
- 장애와 배포 상태

Kafka는 핵심 거래·탐지·사건 기능 안정화 이후 도입할 범위이며 현재 구현된 구성으로 간주하지 않는다.

## 서비스 핵심 영역

### 금융 FDS

- 금융거래와 사용자 행동 이벤트 처리
- Rule 기반 이상거래 탐지
- ML 기반 복합 패턴 보완
- 위험 점수와 설명 가능한 탐지 근거
- 위험 등급별 대응
- 사건 생성·검토·최종 판정
- 조사 및 상태 변경 감사 로그

### AI 운영

- HIGH·CRITICAL 사건 중심 AI 리포트 생성
- 탐지 근거와 고객 행동 타임라인 요약
- 사건 복잡도에 따른 모델 라우팅
- LLM 입력 데이터 축약
- 출력 토큰과 재생성 횟수 제한
- 정확 일치 리포트 캐시
- LLM 실패 시 Rule·ML 기반 템플릿 fallback
- 모델별 호출량·토큰·지연시간·비용 기록

생성형 AI는 위험 점수 계산, 최종 이상거래 판정, 거래 자동 차단, 고객 제재, 사건 상태 자동 확정을 수행하지 않는다.

### Cloud Native 운영

- Spring Boot·FastAPI Health 확인
- PostgreSQL·Redis 상태와 향후 도입할 Kafka 상태 확인
- 배포 버전 확인
- API·Rule·ML·LLM 지연시간 관측
- 오류율과 처리량 관측
- DB Connection Pool 관측
- Kafka 도입 이후 Consumer Lag 관측
- 로그·메트릭·트레이싱 기반 처리 흐름 추적
- 장애 주입과 복구 검증
- AI 호출량·토큰·비용과 FinOps 지표 관리

Docker, Kafka, Kubernetes, AWS, Observability는 로드맵에 따라 단계적으로 도입하는 범위이며 현재 모두 구현된 구성으로 간주하지 않는다.

`AI-FINANCIAL-FDS-PLATFORM`

### 한 줄 설명

금융거래와 사용자 행동을 기반으로 이상거래를 탐지하고, 위험 대응과 사건 처리를 지원하며, AI 서비스의 장애·성능·비용을 통합 관리하는 Cloud Native 금융 AI FraudOps 플랫폼이다.

### 프로젝트 핵심 목표

이 프로젝트는 거래 데이터를 입력하고 AI가 사기 확률을 반환하는 단순 분류 서비스가 아니다. 국내 은행과 핀테크의 FDS 운영 방향을 참고해 다음 전체 흐름을 구현한다.

```text
금융거래·사용자 행동 수집
→ Rule·ML 기반 실시간 위험 분석
→ 위험 점수와 탐지 근거 생성
→ 거래 승인·추가 인증·보류 결정
→ 이상거래 사건 생성
→ FDS 담당자 검토
→ 정상·오탐·이상거래 최종 판정
→ 감사 이력 저장
→ 탐지 정책과 모델 개선
→ 시스템 성능·장애·비용 모니터링
```

실제 금융회사와 동일한 데이터 규모나 외부기관 연동은 구현하지 않는다. 실제 금융회사 FDS의 업무 방향과 운영 구조는 유지하되 데이터 규모, 외부 연동 대상, 트래픽과 서비스 수만 개인 프로젝트 수준으로 조정한다.

## 3. 참고할 금융회사 FDS 방향

### 3.1 은행 FDS에서 가져올 요소

- 계좌이체 이상거래 탐지
- 위험 거래의 추가 인증·보류
- 담당자의 사건 검토
- 정상·오탐·사기 최종 판정
- 모든 처리 이력 저장

### 3.2 하나은행 사례에서 가져올 요소

거래 정보뿐 아니라 다음 기기와 보안 신호를 분석한다.

- 신규 기기
- 기기 신뢰등급
- 악성 앱 탐지 여부
- 원격제어 앱 탐지 여부
- 앱 위변조 신호

실제 악성 앱 탐지 솔루션은 구현하지 않고 가상 보안 신호를 입력받아 위험 분석에 반영한다.

### 3.3 토스 사례에서 가져올 요소

거래 한 건만 분석하지 않고 거래 이전의 행동 흐름을 함께 분석한다.

```text
신규 기기 로그인
→ 비밀번호 변경
→ 이체 한도 상향
→ 신규 수취인 등록
→ 고액 이체
```

자동 탐지 이후 관제 담당자의 처리 흐름도 구현한다.

```text
위험 거래 탐지
→ 사건 자동 생성
→ 담당자 배정
→ 탐지 근거 확인
→ 최종 판정
→ 후속 조치 기록
```

### 3.4 카카오페이 사례에서 가져올 요소

명확한 사고 패턴은 Rule로 탐지하고 복합 패턴은 ML로 보완한다.

```text
Rule 기반 탐지
+ ML 기반 위험 확률
+ 기기 위험정보
+ 외부 위험정보
= 최종 위험도
```

### 3.5 금융권 공동 FDS에서 가져올 요소

의심 계좌, 위험 IP, 위험 기기, 피싱 의심 정보를 제공하는 가상의 외부 위험정보 서비스를 구현한다. 실제 외부기관 데이터는 사용하지 않지만 다음 기술 요소를 구현한다.

- 외부 API 연동
- Timeout
- Retry
- Circuit Breaker
- Fallback
- Redis Cache
- 장애 격리

## 4. 분석 대상

프로젝트는 카드·증권·보험까지 넓히지 않는다. 은행의 디지털뱅킹 영역 안에서 여러 금융거래와 사용자 행동을 연결해 분석한다.

### 4.1 계좌이체

- 내부 계좌이체
- 타행 계좌이체
- 고액 이체
- 최초 수취 계좌 이체
- 반복 이체
- 분산 송금

### 4.2 오픈뱅킹 거래

- 외부 금융기관 계좌 등록
- 외부 계좌 자금 출금
- 여러 외부 계좌의 자금 집중
- 오픈뱅킹 출금 후 즉시 재송금

외부 금융기관은 Mock 서비스로 구현한다.

### 4.3 ATM 현금 인출

- 평소와 다른 지역의 ATM 인출
- 새벽 시간대 반복 인출
- 고액 입금 직후 현금 인출
- 짧은 시간 여러 ATM 사용
- 잔액 대부분 인출

## 5. 사용자 행동 이벤트

금융거래 전후의 다음 행동도 함께 분석한다.

```text
LOGIN
LOGIN_FAILED
DEVICE_REGISTERED
PASSWORD_CHANGED
OTP_REISSUED
BENEFICIARY_REGISTERED
TRANSFER_LIMIT_CHANGED
LOAN_DISBURSED
TRANSFER_REQUESTED
ATM_WITHDRAWAL_REQUESTED
```

예를 들어 고액 이체 한 건만으로는 정상 여부를 판단하기 어렵지만 다음 행동이 연속적으로 발생하면 위험도가 높아진다.

```text
02:01 신규 기기 로그인
02:04 비밀번호 변경
02:07 이체 한도 상향
02:10 신규 수취인 등록
02:13 500만 원 이체
```

이 프로젝트는 단일 거래만 분류하는 것이 아니라 **금융거래와 사용자 행동의 시퀀스**를 분석한다.

## 6. 주요 이상거래 시나리오

### 6.1 신규 기기에서 고액 이체

```text
신규 기기 로그인
→ 최초 수취인 등록
→ 평소 평균의 10배 금액 이체
```

### 6.2 이체 한도 변경 후 송금

```text
비밀번호 변경
→ 이체 한도 상향
→ 짧은 시간 안에 고액 이체
```

### 6.3 외부 위험계좌 송금

```text
계좌이체 요청
→ 외부 위험정보 조회
→ 수취 계좌가 의심계좌와 일치
→ 거래 보류
```

### 6.4 짧은 시간 분산 송금

10분 동안 여러 계좌로 반복 송금한다.

### 6.5 특정 계좌로 자금 집중

여러 고객 계좌에서 동일한 수취 계좌로 송금한다.

### 6.6 송금 후 즉시 ATM 인출

고액 송금 수신 후 짧은 시간 안에 잔액 대부분을 인출한다.

### 6.7 대출 실행 후 자금 이동

```text
대출 실행 이벤트
→ 신규 수취인 등록
→ 대출금 대부분 송금
```

실제 대출 상품과 심사 기능은 구현하지 않고 `LOAN_DISBURSED` 이벤트만 제공한다.

### 6.8 오픈뱅킹 자금 집중

```text
여러 외부 계좌 등록
→ 각 계좌에서 자금 출금
→ 하나의 계좌로 집중
→ 다른 계좌로 즉시 송금
```

## 7. 이상거래 탐지 구조

### 7.1 Rule Engine

초기에는 8~10개의 명확한 Rule을 구현한다.

- 평균 거래 금액의 5배 초과
- 신규 기기에서 거래
- 최초 수취 계좌
- 최근 10분 내 반복 이체
- 해외 IP 접속
- 새벽 시간대 거래
- 거래 직전 비밀번호 변경
- 거래 직전 이체 한도 변경
- 외부 위험계좌 일치
- 악성 앱 탐지 기기
- 입금 직후 ATM 인출

각 Rule은 다음 정보를 가진다.

- Rule ID
- Rule 이름
- 설명
- 조건
- 가중치
- 버전
- 활성화 상태
- 적용 시작일

실행 결과에는 판단 근거를 함께 저장한다.

```json
{
  "ruleCode": "UNUSUAL_AMOUNT",
  "ruleVersion": "1.0",
  "score": 25,
  "evidence": {
    "currentAmount": 5000000,
    "averageAmount": 420000,
    "ratio": 11.9
  }
}
```

### 7.2 ML 기반 탐지

ML은 Rule을 대체하지 않고 복합적인 패턴을 보완한다. 초기 Feature는 다음과 같다.

- 현재 거래 금액
- 평균 대비 거래 금액 비율
- 최근 10분 거래 횟수
- 최근 24시간 거래 금액
- 신규 기기 여부
- 신규 수취 계좌 여부
- 거래 시간대
- 해외 IP 여부
- 비밀번호 변경 후 경과 시간
- 이체 한도 변경 후 경과 시간
- 외부 위험계좌 여부
- 입금 후 출금까지 걸린 시간

초기 모델 후보는 Logistic Regression, Random Forest, XGBoost, Isolation Forest이다. 모델 평가는 정확도 하나로 끝내지 않고 다음 지표를 사용한다.

- Precision
- Recall
- F1-score
- False Positive Rate
- False Negative Rate
- Inference Latency

### 7.3 위험 점수 통합

```text
Rule Score
+ ML Score
+ Device Risk Score
+ External Risk Score
= Final Risk Score
```

예시 위험 등급은 다음과 같다.

| 점수 | 위험 등급 |
| --- | --- |
| 0~29 | LOW |
| 30~59 | MEDIUM |
| 60~79 | HIGH |
| 80~100 | CRITICAL |

가중치와 임계값은 테스트 데이터와 오탐·미탐 결과를 이용해 직접 조정한다.

## 8. 위험 기반 거래 대응

| 위험 등급 | 대응 |
| --- | --- |
| LOW | 거래 승인 |
| MEDIUM | 거래 승인, 모니터링 대상 등록 |
| HIGH | 추가 인증 요구, 이상거래 사건 생성 |
| CRITICAL | 거래 보류, 긴급 사건 생성, 담당자 알림 |

프로젝트에서는 실제 금융거래를 처리하지 않으므로 다음 가상 상태를 사용한다.

```text
RECEIVED
ANALYZING
APPROVED
MONITORING
ADDITIONAL_AUTH_REQUIRED
HELD
BLOCKED
FAILED
```

허용되지 않은 상태 변경은 Spring Boot Service 계층에서 차단한다.

## 9. 이상거래 사건 관리

위험도가 높은 거래는 사건으로 관리하며 하나의 사건에 여러 거래를 연결할 수 있다.

```text
CASE-2026-00031
├── TX-2026-00101
├── TX-2026-00104
└── TX-2026-00108
```

### 9.1 사건 정보

- 사건 ID
- 위험 등급
- 대표 탐지 사유
- 연관 거래
- 연관 계좌
- 담당자
- 처리 상태
- 조사 메모
- 권장 대응
- 최종 판정
- 생성 시간
- 수정 시간

### 9.2 사건 상태

```text
OPEN
IN_REVIEW
ADDITIONAL_INFORMATION_REQUIRED
CONFIRMED_FRAUD
FALSE_POSITIVE
NORMAL
CLOSED
```

사건의 처리 상태와 최종 판정은 별도 필드로 관리한다. `OPEN`, `IN_REVIEW`, `ADDITIONAL_INFORMATION_REQUIRED`, `CLOSED`는 처리 흐름을 나타내고, `CONFIRMED_FRAUD`, `FALSE_POSITIVE`, `NORMAL`은 담당자가 확정하는 최종 판정을 나타낸다.

모든 상태 변경은 감사 로그에 저장한다.

- 변경한 사용자
- 변경 시간
- 이전 상태
- 변경 상태
- 변경 사유
- 관련 거래와 사건

## 10. 생성형 AI의 역할

생성형 AI는 이상거래의 최종 판정자가 아니다.

### 10.1 Rule·ML의 역할

- 위험 점수 계산
- 객관적인 탐지 근거 생성
- 위험 등급 산출

### 10.2 생성형 AI의 역할

- 거래 위험 요약
- 주요 탐지 근거 정리
- 행동 타임라인 설명
- 가능한 위험 시나리오 제안
- 담당자가 확인할 항목 제안
- 권장 대응 리포트 작성

### 10.3 생성형 AI가 하지 않는 것

- 사기 거래 최종 확정
- 거래 차단 직접 실행
- 고객 계정 제재
- 위험 점수 직접 계산
- 사건 상태 자동 확정

LLM에 장애가 발생해도 핵심 FDS 기능은 계속 동작해야 한다.

```text
LLM 정상
→ 생성형 AI 리포트 생성

LLM 타임아웃·장애
→ Rule·ML 결과 기반 템플릿 리포트 생성
```

프롬프트 버전과 사용 모델 버전도 저장한다.

## 11. AI 비용 최적화와 FinOps

AI 비용 최적화는 프로젝트의 부가 기능이 아니라 핵심 목표로 포함한다. 이 프로젝트의 AI 비용 최적화 범위는 다음 항목으로 한정한다.

### 11.1 Rule·경량 ML 기반 사전 분석

전체 거래는 Rule Engine과 경량 ML로 먼저 분석하고 위험 등급을 결정한다. 모든 거래에 생성형 AI를 호출하지 않음으로써 비용과 장애 전파를 줄인다.

```text
전체 거래
→ Rule Engine
→ 경량 ML
→ 위험 등급 결정
```

### 11.2 HIGH·CRITICAL 사건 중심의 LLM 호출

LLM은 HIGH·CRITICAL 사건을 중심으로 호출한다.

```text
LOW
→ LLM 호출 없음

MEDIUM
→ 템플릿 기반 설명

HIGH
→ 경량 생성형 AI 모델 호출

CRITICAL
→ 사건 복잡도에 따라 생성형 AI 모델 호출
```

여러 거래가 연결된 복합 사건, 담당자가 상세 분석을 요청한 사건, 기존 템플릿만으로 설명하기 어려운 사건은 고위험 사건의 상세 분석 조건으로 다룬다. 담당자 수동 요청 시 필요한 경우에만 상세 리포트를 재생성한다.

### 11.3 사건 복잡도에 따른 모델 라우팅

모든 사건에 동일한 고성능 모델을 사용하지 않는다.

```text
단순 사건 요약
→ 저비용 경량 모델

연관 거래가 많고 복잡한 사건
→ 고성능 모델

경량 모델 응답 품질 검증 실패
→ 고성능 모델로 한 번만 재시도
```

라우팅 기준은 다음과 같다.

- 위험 점수
- 연결 거래 수
- 탐지 Rule 수
- 행동 이벤트 수
- 외부 위험정보 존재 여부
- 담당자의 상세 분석 요청 여부

예시 정책은 다음과 같다.

```text
HIGH + 탐지 Rule 2개 이하
→ 경량 모델

CRITICAL + 연관 거래 5개 이상
→ 고성능 모델

응답 JSON 형식 검증 실패
→ 상위 모델로 한 번만 재시도
```

### 11.4 동일 사건의 정확 일치 리포트 캐시

동일한 사건과 동일한 분석 결과에 대해 리포트를 중복 생성하지 않는다. Redis 캐시 키는 다음 정보를 정확히 조합한다.

```text
caseId
+ detectionResultVersion
+ promptVersion
+ modelVersion
```

예시는 다음과 같다.

```text
ai-report:CASE-1001:detection-v2:prompt-v3:model-lite-v1
```

사건이나 탐지 결과가 변경되지 않았다면 저장된 기존 리포트를 반환한다. Rule 또는 분석 결과가 변경되면 캐시를 무효화하고 새 리포트를 생성한다.

이 캐시는 정확 일치 방식만 사용한다. Reason Code가 같다는 이유만으로 다른 사건의 AI 리포트를 재사용하지 않는다.

### 11.5 입력 데이터 요약과 출력 토큰 제한

고객의 모든 거래와 행동 로그를 LLM에 전달하지 않는다. AI 서비스 호출 전에 필요한 데이터만 집계한다.

- 최근 24시간 관련 거래
- 위험도가 높은 행동 이벤트
- 실제로 탐지된 Rule
- 고객 평균 거래 패턴
- 계좌 관계 집계 결과
- 외부 위험정보 요약

구조화된 JSON으로 전달해 불필요한 자연어 입력을 줄인다. 최대 입력 거래 수, 행동 이벤트 수와 출력 토큰 수를 제한한다.

```yaml
ai:
  report:
    max-input-transactions: 20
    max-behavior-events: 15
    max-output-tokens: 700
    max-retries: 1
    daily-regeneration-limit: 3
```

### 11.6 사건별 리포트 재생성 횟수 제한

동일 사건의 불필요한 반복 생성을 막기 위해 사건별 일일 리포트 재생성 횟수를 제한한다. 기본 설정 예시는 `daily-regeneration-limit: 3`이다.

### 11.7 향후 Kafka 기반 비동기 리포트 생성

핵심 거래·탐지·사건 기능이 안정화된 이후 Kafka를 도입해 LLM 리포트 생성을 비동기로 처리하고, 거래 승인 여부를 결정하는 필수 경로에서 분리한다. Kafka 도입 이후에는 중복 메시지가 소비되더라도 같은 리포트가 중복 생성되지 않도록 멱등성을 보장한다.

### 11.8 LLM 장애 시 템플릿 리포트 Fallback

LLM 타임아웃, 장애 또는 응답 검증 실패 시 Rule·ML 결과를 기반으로 템플릿 리포트를 생성한다. LLM 장애가 핵심 거래 분석과 대응에 영향을 주지 않도록 한다.

### 11.9 비용 측정

다음 비용을 측정한다.

- 사건당 AI 리포트 비용
- 거래 1,000건당 AI 비용

### 11.10 비용·응답시간·리포트 품질 비교

Baseline과 Optimized 구조를 비교한다.

#### Baseline 구조

- 모든 거래에 고성능 LLM 호출
- 캐시 없음
- 모델 라우팅 없음
- 전체 데이터를 프롬프트에 포함
- 토큰 제한 없음
- 동일 사건 리포트 중복 생성 허용

#### Optimized 구조

- Rule·ML 기반 사전 선별
- HIGH·CRITICAL 사건 중심의 LLM 호출
- 사건 복잡도에 따른 모델 라우팅
- 동일 사건에 대한 정확 일치 리포트 캐시
- 입력 데이터 요약과 출력 토큰 제한
- 사건별 리포트 재생성 횟수 제한
- 향후 Kafka 기반 비동기 리포트 생성
- LLM 장애 시 템플릿 리포트 Fallback

비용 절감률은 실제 테스트 결과가 나온 뒤 계산한다.

```text
비용 절감률
= (Baseline 비용 - Optimized 비용)
  / Baseline 비용
  × 100
```

비용만 낮추고 리포트 품질이 크게 떨어지면 성공으로 판단하지 않는다. Cost, Latency, Quality를 함께 비교한다.

반복 질문용 시맨틱 캐시와 FDS 챗봇은 핵심 구현 범위에 포함하지 않는다.

## 12. 계좌 관계와 자금 흐름 분석

단일 거래뿐 아니라 계좌 간 자금 흐름을 분석한다.

```text
계좌 A ─┐
계좌 B ─┼──> 계좌 X ───> 계좌 Y
계좌 C ─┘
```

주요 분석 지표는 다음과 같다.

- 최근 24시간 입금자 수
- 최근 24시간 출금 대상 수
- 입금 후 출금까지 걸린 시간
- 입금액 대비 즉시 출금 비율
- 특정 계좌로 집중되는 거래 수
- 하나의 기기에서 접근한 계좌 수

초기에는 PostgreSQL 집계 쿼리로 구현한다. 데이터 규모와 조회 패턴이 증가한 뒤 그래프 데이터베이스 도입 필요성을 검토한다.

## 13. 시스템 아키텍처

처음부터 전체 시스템을 MSA로 분리하지 않고 Spring Boot Modular Monolith를 중심으로 시작한다. Spring Boot는 거래·사건 상태와 업무 정합성의 최종 소유자이며, FastAPI는 Feature 계산, Rule 실행, ML 추론, AI 리포트 생성과 fallback을 담당한다.

아래 구성은 단계적 도입을 포함한 목표 구조이다. Kafka는 핵심 기능 안정화 이후 비동기 사건·리포트·통계 처리에 도입하고, Kubernetes는 핵심 기능과 컨테이너 실행 환경을 검증한 이후 도입한다.

┌─────────────────────────────────────────┐

└──────────┬──────────────────┬───────────┘
           │                  │

┌────────────────────┐  ┌────────────────────┐
│ FastAPI AI Service │  │ External Risk Mock │

## 14. 동기·비동기 처리

### 14.1 동기 처리

```text
거래 요청
→ 기본 검증
→ Rule·ML 위험 분석
→ 위험도 결정
→ 거래 처리 결과 반환
```

고객의 거래 처리 결과와 관련된 흐름은 동기로 처리한다.

### 14.2 비동기 처리

다음 흐름은 Kafka 도입 이후 적용할 비동기 처리 목표이다.

```text
TRANSACTION_ANALYZED 이벤트
→ 사건 생성
→ 담당자 알림
→ AI 리포트 생성
→ 통계 반영
→ 비용 사용량 집계
```

LLM 리포트 생성은 거래 승인 여부를 결정하는 필수 경로에서 분리한다. Kafka 도입 이후 메시지가 중복 소비되더라도 사건, 리포트와 사용량 데이터가 중복 생성되지 않도록 멱등성을 구현한다.

## 20. 포트폴리오에서 강조할 메시지

### 20.1 금융 도메인

> 단일 거래를 분류하는 데 그치지 않고 계좌이체, 오픈뱅킹, ATM 인출과 거래 전후 사용자 행동을 연결해 분석했습니다. 탐지 결과는 위험 기반 대응과 FDS 담당자의 사건 처리로 연결했습니다.

### 20.2 백엔드

> Spring Boot에서 거래 멱등성, 트랜잭션과 상태 전이, 사건 생성, 감사 이력을 관리했습니다. FastAPI 분석 서비스와 외부 위험정보 서비스의 장애를 고려해 타임아웃, 재시도, Circuit Breaker와 Fallback을 설계했습니다.

### 20.3 AI 활용

> Rule과 경량 ML이 객관적인 위험 점수와 판단 근거를 계산하고, 생성형 AI는 고위험 사건의 분석 리포트 작성에만 사용했습니다. 최종 판정과 거래 대응은 백엔드 정책과 담당자가 통제하도록 설계했습니다.

### 20.4 클라우드·DevOps

> 핵심 기능을 먼저 안정화한 뒤 Docker 실행 환경, Kafka 비동기 처리, Kubernetes·AWS 배포를 단계적으로 검증합니다. 각 단계에서 거래 요청부터 AI 분석과 사건 처리까지 로그·메트릭·트레이싱으로 추적하고, 장애 시나리오와 복구 과정을 검증한 결과만 문서화합니다.

### 20.5 AI 비용 최적화·FinOps

> 모든 거래에 생성형 AI를 호출할 때의 비용과 장애 영향을 통제하기 위해 Rule과 경량 ML로 전체 거래를 선별하고, HIGH·CRITICAL 사건을 중심으로 생성형 AI를 호출합니다. 사건 복잡도에 따른 모델 라우팅, 정확 일치 리포트 캐시, 입력 데이터 요약, 출력 토큰과 재생성 횟수 제한을 적용합니다. LLM 장애 시 템플릿 Fallback으로 핵심 처리 경로를 보호하고, Kafka 기반 비동기 생성은 핵심 기능 안정화 이후 도입합니다. 거래 1,000건당 AI 비용과 사건당 리포트 비용은 실제 호출 기록을 측정한 뒤 비용·응답시간·품질과 함께 비교합니다.

## 21. 프로젝트 소개 문장

> 국내 은행과 핀테크의 FDS 사례를 참고해 실시간 탐지, 위험 기반 대응, 담당자 사건 처리, 외부 위험정보 연계, 운영 모니터링이라는 공통 구조를 도출한다. 이를 바탕으로 계좌이체, 오픈뱅킹, ATM 인출과 사용자 행동 이벤트를 분석하는 FinGuardOps를 구현한다. Spring Boot에서 거래 정합성과 사건 상태를 관리하고, FastAPI가 Rule·ML 분석과 생성형 AI 리포트·fallback을 담당하도록 구성한다. Redis 정확 일치 캐시와 모델 라우팅, 토큰 사용량·비용 계측을 적용하며, Kafka 비동기 처리와 Kubernetes·AWS 배포, 로그·메트릭·트레이싱은 핵심 기능 안정화 이후 단계적으로 도입하고 검증한다.
